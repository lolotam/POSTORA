# Agent Procedures — Spec B: store-event flows

Date: 2026-09-27. Status: approved (user answered the six scoping questions and approved sections 1–2; the advisor settled sections 3–4 under the session goal).
Builds on Spec A (`2026-09-26-agent-procedures-a-design.md`, PR #209, follow-ups PR #211).

## 1. What this adds

Three flows the **business** starts from a WooCommerce event, on WhatsApp only:

| Key | Trigger | Opener asks | End action |
|---|---|---|---|
| `cod_confirm` | new COD order | confirm or cancel | Confirm → order note; Cancel → status `cancelled` + note |
| `review_request` | order became `completed`, N days later | rating 1–5 | 4–5 → owner's review link; 1–3 → ask the problem, hand off with a summary |
| `back_in_stock` | a waitlisted product is `instock` | want the link? | yes → product link + current price; no → end |

Instagram and Facebook are out of scope: they need message tags the code does not support and an order carries no Instagram/Facebook identity.

Both WhatsApp connection modes are supported (user decision C):
- **Cloud API / coexistence:** the opener is a Meta-approved template (outside the 24-hour window nothing else is allowed).
- **QR (`evolution_qr`):** templates are impossible; the opener is free text, capped at 50 openers per account per day.

## 3. Architecture (approach 1: persist events, send from a worker)

```
WooCommerce ──HMAC──▶ store-webhook ──filter──▶ store_events (due_at)
                                                  │  cron every minute
                                                  ▼
                                      process-store-events (claim + lease)
                                        resolve chat · opt-out · caps
                                        send opener (template | text)
                                        start procedure (CAS expected null)
customer reply ──▶ ai-agent-reply (existing) ──▶ procedure continues ──▶ end action
```

### 3.1 `store-webhook` (public, no JWT)
- URL: `/functions/v1/store-webhook/<social_account_id>/<connector_id>`. Both ids must belong to the same user, the connector must be `woocommerce`, and the account must be WhatsApp.
- **Ping:** WooCommerce saves an active webhook by POSTing an unsigned form body `webhook_id=<n>`. That exact shape gets a 200 and nothing is stored (a non-2xx can disable the webhook).
- **Signature:** `X-WC-Webhook-Signature` = base64(HMAC-SHA256(raw body, secret)); constant-time compare. `X-WC-Webhook-Source` must match the connector's `store_url` host. Any failure → 401 with no detail.
- **Secret:** 32 random bytes generated by Postora per connector, stored through the existing connector-credential path, shown once in the card, rotatable. Never logged.
- Body cap 256 KB; rate limit per connector and per IP with `check_rate_limit`.
- **Filter before insert** (only what a flow needs is stored):
  - `order.created`, `payment_method = 'cod'`, status not in {cancelled, refunded, failed, completed} → `cod_confirm`, due now. (WooCommerce puts COD orders in `processing`; the payload is built at delivery time.)
  - `order.updated` with status `completed` → `review_request`, due `now + review_delay_days`.
  - `product.updated` with `stock_status = 'instock'` **and** at least one un-notified waitlist row for that product or its parent → one `back_in_stock` event per waiting customer. Anything else is dropped.
  - Each flow's toggle must be on for the account, else dropped.
- Always answers 200 quickly once the signature is valid (even for dropped events), so WooCommerce does not retry.

### 3.2 Data (migration, Muse Spark lane)
- `store_events`: `id`, `user_id`, `social_account_id`, `connector_id`, `flow`, `external_id` (order id or `<product id>:<waitlist id>`), `delivery_id`, `payload` (**minimal** jsonb: order id/number, normalized phone, first name, total + currency, status, payment method, product id/name), `status` (`pending|claimed|sent|skipped|failed`), `outbound_message_id`, `skip_reason`, `due_at`, `claimed_at`, `attempts`, `created_at`, `processed_at`. Unique `(connector_id, flow, external_id)` so retries and re-completions never send twice. Service-role only: RLS on, no policies for `anon`/`authenticated`, `REVOKE ALL` from `PUBLIC, anon, authenticated`. Rows purged 30 days after processing.
- `stock_waitlist`: `id`, `user_id`, `social_account_id`, `conversation_id`, `phone`, `product_id`, `parent_id`, `product_name`, `created_at`, `notified_at`, `expires_at` (created + 60 days). Unique `(social_account_id, phone, product_id)` where `notified_at is null`. Owner can read and delete their rows (RLS by `user_id`); writes are service-role.
- `messaging_opt_outs`: `user_id`, `phone`, `created_at`, `source`. Unique `(user_id, phone)`. Owner read/delete; writes service-role.
- Extend `ai_agent_test_expected_valid` only if a new intent is added (none is planned).
- Cron job `process-store-events`, every minute.

### 3.3 `process-store-events` (worker, cron-authed)
- Claims up to 20 due rows with `FOR UPDATE SKIP LOCKED` **and** a `claimed_at` lease of 2 minutes (a row claimed longer ago is reclaimable); `attempts` capped at 3, then `failed`.
- For each event:
  1. Skip if the flow is now disabled, the account's agent is disabled or its engagement mode would not let the AI reply (`human_first` blocks unconditionally), the phone is opted out, the event is older than `due_at + 48h`, or (QR) the account already sent 50 openers today. `review_request` re-reads the order and skips unless it is still `completed` (it may have been refunded during the delay).
  2. Build the conversation id for the account's mode; find or create the `ai_threads` row.
  3. Start the procedure with `persistProcedureState(expected = null)`, `run_id = store_events.id`, `origin = "event"`. A non-null state → `skipped: flow_active`, **except** a state with `origin = "event"` and `run_id = store_events.id`: that is this event's own unfinished attempt (a worker died between start and send), so it resumes at step 4.
  4. Send the opener, idempotently: if the event row already records an `outbound_message_id`, do not send again. Cloud API: the approved template in the account's language (default Arabic; WooCommerce carries no customer language); not approved → `skipped: template_not_approved` and the state is cleared with a CAS. QR: the same wording as the template body, in the account language, as free text. The provider message id is written to the event row immediately after the send.
  5. Record the opener in `whatsapp_messages` (inbox) and in the thread's message history so the model sees it when the customer replies.
  6. Mark `sent` (or `failed` with a sanitized reason; on send failure the state is cleared with a CAS).
- Purges processed `store_events` older than 30 days and expired waitlist rows.

### 3.4 Engine and runtime changes
- Templates gain `cod_confirm` (field `decision`: confirm|cancel), `review_request` (`rating` 1–5, then `problem` only when rating ≤ 3), `back_in_stock` (`interest`: yes|no). A field can be conditional on an earlier field (needed for `problem`).
- **Expiry by origin:** event-started flows expire after 72 hours (customers answer templates late); Spec A flows keep 24 hours.
- `jevStartKey` never starts an event flow; the model cannot `start_procedure` an event flow either (only the worker can).
- New end actions:
  - `cod_update`: re-read the order; if its status changed since the event (or is cancelled/completed), write nothing, alert the admin, tell the customer the team will follow up. Else Confirm → note "Confirmed by the customer on WhatsApp (Postora)"; Cancel → status `cancelled` + note.
  - `review_route`: 4–5 → send the configured review link; 1–3 → escalate with rating and problem.
  - `stock_offer`: yes → store lookup for the product (link + price); no → end.
  - All go through the PR #211 claim first.
- Waitlist join: a new agent tool `stock_waitlist_join(product_id)` offered only when `back_in_stock` is enabled and a stock check in this turn returned out of stock for that product; the runtime takes product id/name/parent from that stock result, never from free model text.
- Opt-out is detected at **inbound ingest**, before auto-reply rules and agent dispatch, in both `whatsapp-webhook` and `whatsapp-evolution-webhook`, through one shared helper (`_shared/optOut.ts`). A whole message (trimmed, case-insensitive) of stop/unsubscribe/إلغاء الاشتراك/توقف writes `messaging_opt_outs` and clears any active event-origin flow with a CAS. It therefore works when the agent is off or human-first.

### 3.5 Store writes
- New WooCommerce adapter capability `update_order` (status + note) — the only write. The adapter refuses it while the tool's `read_only_mode` is true (preserves PR #204). The existing "writes are refused" test stays for every other capability.
- The card will not enable `cod_confirm` while the connector is read-only and says why. A 401/403 at end time → admin alert; the customer is told the team will follow up.

### 3.6 Templates (Cloud API)
- Postora submits `postora_cod_confirm_v1` (UTILITY, quick replies Confirm/Cancel), `postora_review_request_v1` (UTILITY), `postora_back_in_stock_v1` (MARKETING), each in Arabic and English, when the flow is enabled. It lists existing templates first and reuses a matching name.
- Status is read with `whatsapp_list_templates` when the card loads and when the worker meets a non-approved template. No new Meta webhook subscription. The card shows pending/approved/rejected and the category Meta assigned.

### 3.7 Settings (Procedures card)
- Per flow: enable toggle (refused unless the account's agent is enabled and can reply; `cod_confirm` also refused while the connector is read-only); `review_request` adds delay days (0–14, default 3) and review link (https only); the card shows the webhook URL and a "Generate / rotate secret" button for the account's WooCommerce connector, and the WooCommerce topics to add.
- Stored in `agent_behavior.procedures` like Spec A, parsed strictly on save and leniently on read.

## 4. Security
- Public endpoint: HMAC with constant-time compare, source host check, per-connector and per-IP limits, body cap, no detail in errors, raw payload never stored or logged.
- `store_events` is service-role only; PII minimal; 30-day purge.
- Phone numbers normalized by one shared function (`_shared/phone.ts`, seeded with `billing.country` when there is no `+`); `ecommerce-whatsapp-api`'s private copy is replaced by it.
- The worker never sends to a phone without an order or waitlist row naming it; QR daily cap; opt-out honoured before every send.
- Secrets: webhook secret and Woo keys only via the credential path; never in logs, briefs or fixtures.

## 5. Testing
- Deno: signature verify (valid, wrong secret, missing header, the ping shape) with a mutation check; event filter per topic; phone normalization table; conversation id per mode; worker claim/lease/attempts; opt-out; engine expiry by origin; conditional field; each end action including the status-changed guard and the read-only refusal; waitlist join only from a stock result.
- SQL suite `supabase/tests/agent_procedures_b.sql`, registered in `SUITES` with the sentinel: tables, uniques, RLS/grants (anon and authenticated cannot read `store_events`), cron job exists.
- Vitest: card toggles, read-only COD refusal, review settings validation, webhook URL display.
- Live: replay a captured WooCommerce payload with a valid HMAC against production for the admin's connector with a dry-run event flag (worker resolves and logs, no send); one real send only to the admin's own test number.
