## Rules and traps for the implementing agent

Read these before the reference. Each one is a mistake an implementation makes when it has the contract and nothing else.

1. **Workspace routes authenticate with `x-postora-key`, nothing else.** Platform routes under `/v1/platform/` use `Authorization: Bearer pl_live_…` (or `x-postora-key` with that platform key). These are separate credentials and scopes. Test keys (`pk_test_` / `pl_test_`) never work against production; live keys never work against staging.
2. **Every `POST /v1/messages`, `POST /v1/media`, `POST /v1/posts`, `POST /v1/connectors/{type}/connect-link` and `POST /v1/tools/execute` carries an `Idempotency-Key`.** Generate one UUID per logical operation, store it with the operation, and reuse it on every retry of that operation. A new key on retry is a duplicate send. `POST /v1/posts/{id}/schedule` and the webhook routes do not take one.
3. **Retry only when `error.retryable` is `true`.** Never decide from the HTTP status family: `temporarily_unavailable` is a 503 that is NOT retryable, `idempotency_in_progress` is a 409 that IS. Back off exponentially and honour `Retry-After` when present.
4. **For messaging, `idempotency_indeterminate` means "may have been delivered". Do not resend.** Not with the same key (it will answer the same 409) and not with a new one (that is a second real message to a real customer). Reconcile: wait for the `message.accepted` webhook, or list the conversation's messages and match `provider_message_id`. For platform provisioning, reconcile the workspace estate as described in rule 16.
5. **A replay is not a new send.** The same key and the same body return the stored response with `Idempotency-Replayed: true`. The same key with a different body is `idempotency_conflict`; that is a bug in the caller, not a transient.
6. **Verify webhook signatures over the exact raw request bytes.** `X-Postora-Signature` is `sha256=<hex>` of HMAC-SHA256(secret, `<X-Postora-Timestamp>.<raw body>`). Sign the bytes you received, before any JSON parsing or re-serialisation; compare in constant time; reject timestamps older than your own replay window (we suggest 5 minutes). Then answer 2xx quickly and process asynchronously: anything else is retried on a 1m / 5m / 30m / 2h / 6h ladder.
7. **Deduplicate webhooks on `X-Postora-Event-Id`.** Delivery is at-least-once and ordering is not guaranteed; a `message.delivered` can arrive before the `message.accepted` it follows.
8. **404 `resource_not_found` is also the answer for "exists, but not yours".** Anything outside the accounts bound to the key answers 404, never 403. Do not read a 404 as "wrong URL" until you have checked the id belongs to a bound account.
9. **Only what this key created through the API is addressable.** A post made in the Postora UI answers 404 on every `/v1/posts` route, permanently. There is no `POST /v1/posts/{id}/publish`: schedule it and the scheduler publishes.
10. **Reference media by `media_id`, never by URL.** Upload first (`POST /v1/media`), then send. `media_pending` (409, retryable) means retry the SAME request later; `media_rejected` (422) means that file will never send.
11. **`type: template` sends are suspended** (503 `temporarily_unavailable`, not retryable) as a policy state. Text and media sends are live. Build the template path against the contract, but do not treat its 503 as an outage to poll.
12. **Treat every id as opaque.** Ids are prefixed (`acc_`, `conv_`, `msg_`, `media_`, `post_`, `wh_`); never parse or construct them. `message_id` returned by a send is the provider's id (a WhatsApp `wamid`), which is a different thing from a `msg_` id. The connector routes are the one exception: `tool_id`, `social_account_id` and `connection_id` there are bare UUIDs, still opaque — take them from `GET /v1/connectors` and pass them back unchanged.
13. **Page with `next_cursor` until it is `null`.** It is always present on a listing; `null` is the only terminator.
14. **Tolerate unknown fields and enum values.** The contract is additive-only; a client that fails on a new optional field will break on the next release. Breaking changes only ever arrive under a new path prefix.
15. **Log `X-Postora-Request-Id` with every call** (it is also `request_id` in every body, success or error). It is the only handle support has for "this call returned the wrong thing".
16. **Platform provisioning returns its bootstrap secret once.** Reuse `external_ref` to recover existing workspace metadata, then issue a new key with an explicit account UUID if the secret was lost. Unresolved attempts answer `idempotency_indeterminate`: reconcile before provisioning again. Platform workspace/account/key ids are bare UUIDs. Ownership belongs to the principal and survives platform credential rotation.

## Quick facts

- **Workspace auth:** header `x-postora-key: pk_live_…` (production) or `pk_test_…` (staging).
- **Platform auth:** `Authorization: Bearer pl_live_…` (production) or `pl_test_…` (staging); `x-postora-key` also accepted. Platform credentials provision workspaces and issue/revoke their workspace keys; they cannot access workspace resources.
- **Success envelope:** the resource, or `{ "data": [...], "next_cursor": string | null }` for listings; `request_id` in every body.
- **Error envelope:** `{ "error": { "code", "message", "retryable", "request_id", "details"? } }`.
- **Correlation:** `X-Postora-Request-Id` on every response.
- **Rate limit headers:** `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`; `Retry-After` on 429 when computed.
- **Certified webhook events:** `webhook.test`, `message.received`, `message.accepted`, `message.delivered`, `message.read`, `message.failed`, `account.reauthorization_required`, `post.scheduled`.

## Getting Started

You need an operator-issued partner key before you can call the Partner API. There is no self-service UI for partner keys in v1.

### 1. Obtain a key

Contact your Postora operator. The operator mints the key with `scripts/create-partner-key.ts` using a user JWT (service-role is refused) and gives you the plaintext once. Store it securely — it is shown once and stored only as a SHA-256 hash.

Keys are environment-bound (`pk_live_` for production, `pk_test_` for staging). See `authentication.md`.

### 2. First call

List the accounts bound to your key:

```bash
curl -H "x-postora-key: pk_live_REPLACE_ME" \
  https://api.postora.cloud/functions/v1/partner-api/v1/accounts
```

Success is `200` with a `CollectionEnvelope` containing `data: Account[]`, `next_cursor: null`.

### 3. Read the request ID

Every response — success or error — carries `X-Postora-Request-Id`. The same value appears inside the v1 error envelope as `error.request_id`. Include it when asking for support.

```bash
curl -i -H "x-postora-key: pk_live_REPLACE_ME" \
  https://api.postora.cloud/functions/v1/partner-api/v1/accounts | grep -i x-postora-request-id
```

### Next steps

- `authentication.md` — header name and environment rule.
- `scopes.md` — which scope your key needs.
- `errors.md` — how to read failures.

Reference: `docs/api/openapi.yaml` paths `/functions/v1/partner-api/v1/accounts` and `components.headers.X-Postora-Request-Id`.

## Authentication

### Header

Send your key in `x-postora-key`:

```
x-postora-key: pk_live_REPLACE_ME
```

`Authorization: Bearer` is not read by the Partner API. The alias and `/v1` read only `x-postora-key` (`supabase/functions/partner-api/index.ts`, `supabase/functions/_shared/partnerApiKeys.ts:104`).

### Key prefixes and environments

- `pk_live_` — production (`PARTNER_API_ENVIRONMENT=production`, the default when unset).
- `pk_test_` — staging (`PARTNER_API_ENVIRONMENT=staging`).

A staging key never authenticates against production and a production key never authenticates against staging. The door checks the prefix before any database lookup and answers `invalid_key` 401 for a cross-environment key, indistinguishable from an unknown key (`partnerApiKeys.ts:104-131`).

### Non-enumerable 401

Unknown, malformed and other-environment keys share the non-enumerable `invalid_key` 401 — no body reveals whether the key exists. `key_revoked` and `key_expired` are distinct codes answered after a successful lookup, so they do confirm the key existed. Do not branch on message text — branch on `code`.

### Expiry and revocation

- `expires_at` — when set, the key answers `key_expired` 401 after that instant (`partnerApiKeys.ts:137`).
- `revoked_at` — when set, the key answers `key_revoked` 401 (`partnerApiKeys.ts:134`).

Revocation is one-way. A revoked key cannot be un-revoked — the operator must mint a new one.

Reference: `supabase/functions/_shared/partnerApiKeys.ts` and `docs/api/openapi.yaml` `components.securitySchemes.PartnerApiKey`.

## API Keys — Lifecycle

There is no self-service UI for partner keys in v1. All lifecycle operations are operator-run.

### Issue

Operator runs `scripts/create-partner-key.ts` with `--token <user JWT>` (or `SUPABASE_USER_JWT`) plus `--workspace`, `--account`, `--name`, `--scopes`, `--quota`, `--environment`. The service-role key is refused. The plaintext is printed once; only `key_hash` and `key_prefix` are persisted. The account must be an active WhatsApp account in that workspace.

Contact your operator with the workspace, the `acc_` account to bind, and the generic scopes you need (see `scopes.md`). You will receive a `pk_live_REPLACE_ME` or `pk_test_REPLACE_ME`.

### Rotate with overlap

Rotation has built-in overlap via `scripts/rotate-partner-key.ts --overlap <minutes>` (default 60, maximum 43200 = 30 days, never extends an existing `expires_at`). The old key's `expires_at` is set to the end of the window; it stops authenticating when the window closes.

1. Operator runs `scripts/rotate-partner-key.ts --key <uuid> --overlap 60 --token <user JWT>`.
2. Deploy the new key (plaintext shown once) before the deadline printed by the script.
3. After the deadline the old key is expired; no revocation step is needed.

During overlap both keys are valid.

### Revoke

Revocation sets `revoked_at` and immediately returns `key_revoked` 401. It is one-way.

### What a partner must do at rotation

- Never log the plaintext.
- Update the `x-postora-key` header in all callers before the overlap deadline.
- Deploy within the window; if the old key was already time-boxed to sooner, the earlier deadline wins.

Reference: `scripts/create-partner-key.ts`, `supabase/functions/_shared/partnerApiKeys.ts`.

## Scopes

A scope is a capability grant on the key. The Partner API authorises by *action*, and an action lists the scopes that satisfy it (`supabase/functions/_shared/partnerScopes.ts`, `supabase/functions/partner-api/router.ts` `ACTION_SCOPES`).

An unknown scope satisfies nothing. `insufficient_scope` is `403` with `retryable: false` — permanent for that key until the operator reissues it with a broader grant.

New keys may hold only generic scopes. Legacy `whatsapp:*` scopes are accepted at frozen capability for existing keys only and are not issuable to new ones (see `deprecations.md`).

### Route → scope

| Route | Scope |
|---|---|
| `GET /v1/accounts`, `GET /v1/accounts/{id}` | `accounts:read` |
| `GET /v1/conversations`, `GET /v1/conversations/{id}` | `conversations:read` |
| `GET /v1/conversations/{id}/messages` | `messages:read` |
| `GET /v1/messages/{id}` | `messages:read` |
| `POST /v1/messages` — `type: text` or media (`image`,`video`,`audio`,`document`) | `messages:send` |
| `POST /v1/messages` — `type: template` | `messages:send` **or** legacy `whatsapp:template.send` |
| `GET /v1/templates` | `templates:read` (or legacy `whatsapp:templates.read`) |
| `POST /v1/media` | `media:write` |
| `GET /v1/media/{id}` | `media:read` |
| `GET /v1/usage` | `usage:read` |
| `POST /v1/posts` | `posts:write` |
| `GET /v1/posts/{id}` | `posts:read` |
| `GET /v1/posts/{id}/status` | `posts:read` |
| `POST /v1/posts/{id}/schedule`, `DELETE /v1/posts/{id}/schedule` | `posts:schedule` |
| `GET /v1/connectors` | `connectors:read` |

## Pagination

List routes use opaque cursor pagination (`limit`, `cursor`, `next_cursor`). There is no offset/page-number mode.

### Parameters

- `limit` — page size. Bounds and default are defined in `docs/api/openapi.yaml` `components.parameters.Limit` and enforced in `supabase/functions/partner-api/v1/pagination.ts` (`LIMIT_MIN`, `LIMIT_MAX`, `LIMIT_DEFAULT`). Cite the document for the numbers; the code clamps to them.
- `cursor` — opaque string from a previous `next_cursor`. Do not construct or decode it.

### Response

Every listing returns `CollectionEnvelope` with `data: []` and `next_cursor: string | null`. When `next_cursor` is `null` there is no next page. Some listings (accounts, templates, webhooks) always return `null` because they are bounded.

### Cursors

Cursors are base64url of `{"t": timestamp, "i": id}` ordered by `(timestamp, id)` descending. An invalid cursor answers `invalid_request` 400. A tampered cursor never silently resets to page 1.

Loop as:

```
cursor = null
do {
  page = GET /v1/conversations?limit=20&cursor=cursor
  process(page.data)
  cursor = page.next_cursor
} while (cursor !== null)
```

Reference: `supabase/functions/partner-api/v1/pagination.ts` and `docs/api/openapi.yaml` `components.schemas.CollectionEnvelope`.

## Idempotency

Every side-effecting POST requires `Idempotency-Key`. Missing key → `missing_idempotency_key` 400.

Covered routes: `POST /v1/messages`, `POST /v1/media`, `POST /v1/posts`, `POST /v1/connectors/{type}/connect-link`, `POST /v1/tools/execute`. `POST /v1/posts/{id}/schedule` and every webhook route do not require it — setting the same schedule twice is the same state; a duplicate subscription is harmless. Webhook routes deliberately do not require it.

A refusal that happens *before* the request reaches a connector never consumes the key: on `POST /v1/tools/execute` every authorisation and capability refusal (`tool_not_found`, `connector_tool_not_allowed`, `connector_write_not_allowed`, `connection_inactive`, `connector_unavailable`) is deterministic and is answered without claiming, so the same key still works on the next attempt.

### Same key + same body → replay

The stored response (status + body) is replayed verbatim, with `Idempotency-Replayed: true` — every `/v1` replay carries this header. No second side effect occurs. The body hash is canonical (sorted keys), so key ordering does not matter (`supabase/functions/_shared/partnerApiIdempotency.ts`).

### Same key + different body → conflict

`idempotency_conflict` 409, `retryable: false`. The key is bound to the first body. Use a new key for a different request.

### In-progress

Concurrent retry while the first attempt is still processing returns `idempotency_in_progress` 409, `retryable: true`. Retry after backoff with the same key and same body. The lease is 300s (`p_lease_seconds`); after expiry a new caller may take over.

### Indeterminate

`idempotency_indeterminate` 409, `retryable: false`. Means the outcome is unknown and may have been delivered. **Do not retry.** A `POST /v1/tools/execute` that answered `tool_execution_timeout` (504) lands here on the next attempt with the same key, deliberately: the connector call may already have taken effect, so reconcile in the connected system rather than executing again. For a send, reconcile by listing the conversation's messages (`GET /v1/conversations/{id}/messages`) and matching `provider_message_id` to the wamid you received on the accepted send, or wait for `message.accepted` (payload `message_id` = wamid). Contact support with `X-Postora-Request-Id` if needed. A taken-over `intended` dispatch never re-calls the provider (see `messaging.md`).

Reference: `supabase/functions/_shared/partnerApiIdempotency.ts` header comment and `docs/api/openapi.yaml` `components.parameters.IdempotencyKey`.

<!-- docs/developer/rate-limits.md -->

## Rate Limits

Per-key, per-minute, enforced by `consume_partner_rate_v2` (`supabase/functions/_shared/partnerApiMetering.ts`).

### Headers

- `X-RateLimit-Limit` — configured limit for the key (`rate_limit_per_min`).
- `X-RateLimit-Remaining` — requests remaining in the current window.
- `X-RateLimit-Reset` — seconds until the current window ends (1..60, from Postgres).

On success the three headers are set. On `rate_limited` 429 the response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining: 0` and, when the limiter supplied a reset, `X-RateLimit-Reset` and `Retry-After` (same value); `Retry-After` may be absent if no reset was computed. Pre-auth failures omit rate-limit headers.

### Errors

- `rate_limited` 429, `retryable: true` — back off for `Retry-After` seconds.
- `limiter_unavailable` 503, `retryable: true` — the limiter itself is down; retry shortly.

### Why reads may proceed during a limiter outage while writes refuse

The limiter classifies actions by risk (D7). Class A — bounded local reads (`GET /v1/accounts`, `/v1/conversations`, `/v1/messages/{id}`, `GET /v1/usage`, `GET /v1/webhooks`, `GET /v1/webhooks/{id}`, etc.) — fails **open** when the limiter is unavailable, because letting a read through unthrottled has bounded cost. Class B and C — unbounded or mutating operations (`GET /v1/templates`, `POST /v1/messages`, `POST /v1/media`, `POST /v1/posts`, webhook mutations) — fail **closed** with `limiter_unavailable`, because unmetered writes or outbound calls during an incident compound the outage.

Reference: `supabase/functions/_shared/partnerApiMetering.ts` `LimiterRiskClass`, `docs/api/openapi.yaml` per-path `D7 class A/B/C` notes.

<!-- docs/developer/quotas.md -->

## Quotas

Monthly per-key send quota (`partner_api_keys.monthly_quota`). When `null`, the key is uncapped.

### Meters

`GET /v1/usage` (`supabase/functions/partner-api/v1/usage.ts`) reports:

```json
{"period":{"start":"<last_reset_at>","end":"<next month UTC>"},"meters":[{"meter":"messages","limit":null,"reserved":0,"confirmed":0,"indeterminate":0,"charged":0}],"rate_limit":{"per_minute":60},"request_id":"<uuid>"}
```

- `reserved` — in-flight sends (quota held before provider call).
- `confirmed` — provider accepted.
- `indeterminate` — outcome unknown.
- `charged` — sum of the three, the number that counts against `limit`.
- `limit` — the monthly cap or `null`.
- `period.start` is `last_reset_at` (not necessarily the 1st); `period.end` is the next calendar month in UTC.
- `rate_limit.per_minute` and top-level `request_id` are also returned.

### What is charged

`charged = reserved + confirmed + indeterminate`. A reservation held while a dispatch is in flight is charged. A `confirmed` transition keeps it charged. An `indeterminate` outcome also stays charged — it may have been delivered, so the quota is held rather than refunded. Only a definite provider rejection releases the reservation.

### Errors

`quota_exceeded` 429, `retryable: false`. The period does not reset until the next calendar month; retrying within the same period will not succeed. Back off until `period.end` or ask the operator to raise the quota.

Reference: `supabase/functions/partner-api/v1/usage.ts` and `docs/api/openapi.yaml` `/functions/v1/partner-api/v1/usage` `UsageResponse`.

## Errors

### Envelope

Every `/v1` failure uses one envelope:

```json
{
  "error": {
    "code": "rate_limited",
    "message": "Rate limit exceeded",
    "retryable": true,
    "request_id": "018f3a2e-7b1a-7c9d-9e0f-1a2b3c4d5e6f",
    "details": { "meta_code": 131047 }
  }
}
```

`code` is stable — branch on it. `message` is human-readable and not stable. `details` is optional. `request_id` equals the `X-Postora-Request-Id` response header.

The alias (`POST /functions/v1/partner-api`) uses a different envelope (`{success:false, error:{…}, request_id}`) deliberately. Do not unify them.

### Retry verdict

**The typed `retryable` boolean is the retry verdict, never the HTTP status family.** This is the D2 divergence from the PRD and is stated here as such. Example: `temporarily_unavailable` is `503` with `retryable: false` (policy suspension), while `limiter_unavailable` is `503` with `retryable: true`.

Act only on `retryable: true`. A `503` with `retryable: false` will never succeed by retrying.

### Request ID for support

Include `error.request_id` / `X-Postora-Request-Id` when contacting support. It correlates the client error with server logs.

### Where the codes live

Do not copy the table into prose. The authoritative list is `docs/api/openapi.yaml` `components.schemas.V1ErrorCode` and the single policy table `supabase/functions/partner-api/v1/errors.ts` (`V1_ERROR_POLICY`) that pins each code's status and retryable flag.

## Webhooks

### Subscribe

- `POST /v1/webhooks` — `url` (public HTTPS), `events` (certified types only). Response carries `secret` once.
- `GET /v1/webhooks`, `GET /v1/webhooks/{id}` — reads never return `secret`.
- `PATCH /v1/webhooks/{id}` — update `url`, `events`, `is_active`. Setting `is_active: true` clears a disabled reason.
- `DELETE /v1/webhooks/{id}` — deletes queued deliveries with it.
- `POST /v1/webhooks/{id}/rotate-secret` — returns new `secret`; previous secret verifies for 24h (`previous_secret_expires_at`).
- `POST /v1/webhooks/{id}/test` — queues a `webhook.test` event, answers `202`. Refused unless the subscription is active and subscribed to `webhook.test`.

Scope: `webhooks:read` for reads, `webhooks:manage` for mutations.

### Signature verification

Each delivery carries:

- `X-Postora-Event` — event type.
- `X-Postora-Event-Id` — delivery row id (`evt_` prefix), immutable across retries.
- `X-Postora-Timestamp` — seconds since epoch when the signature was computed.
- `X-Postora-Signature` — `sha256=<hex>` of `<timestamp>.<raw body>` signed with HMAC-SHA256 under the subscription's secret.

Worked verification (signing line and header names match `supabase/functions/_shared/partnerWebhookDelivery.ts`):

```
expected = HMAC_SHA256(secret, timestamp + "." + rawBody)  // rawBody = exact bytes POSTed
           hex-encoded and prefixed "sha256="  // over `${timestamp}.${body}`
if expected != header["X-Postora-Signature"] → reject
// Receiver's own replay window — we suggest 5 minutes:
if abs(nowSeconds - header["X-Postora-Timestamp"]) > 300 → reject
```

The secret used is the one captured at enqueue (`secret_version`). Past the 24h overlap a retry is delivered under the new secret and `reVersioned` is recorded.

### Dedupe, retries, ordering

- Deduplicate on `X-Postora-Event-Id`. Retries carry the same id.
- Retry ladder: `1m / 5m / 30m / 2h / 6h`, then exhausted. Any non-2xx (including 4xx) is retried until ladder exhaustion. `MAX_DELIVERY_ATTEMPTS = 6`.
- Ordering is not guaranteed — handle out-of-order delivery.

### Certified event types

Read `supabase/functions/_shared/partnerWebhookEvents.ts` `CERTIFIED_EVENT_TYPES`: `webhook.test`, `message.received`, `message.accepted`, `message.delivered`, `message.read`, `message.failed`, `account.reauthorization_required`, `post.scheduled`. No other name is subscribable.

Reference: `supabase/functions/_shared/partnerWebhookDelivery.ts`, `docs/decisions/2026-09-02-d5-webhook-substrate.md`, `docs/api/openapi.yaml` `/functions/v1/partner-api/v1/webhooks`.

## Messaging

### Send

`POST /v1/messages` with `Idempotency-Key`. Scope `messages:send` (or legacy `whatsapp:template.send` for `type: template` only).

Types: `text` (`text.body`), `template` (`template.name`, `template.language` defaults `en_US`), media (`image`,`video`,`audio`,`document` referencing `media_id` from `POST /v1/media`). `caption` is forbidden for `audio`.

Capability is checked at the door via the Phase 9 matrix (`connection_mode × type`) before any side effect. QR-mode (`evolution_qr`) accounts answer `unsupported_direct_qr` 400 for every type.

### Template sends currently suspended

All `type: template` requests answer `temporarily_unavailable` `503` with `retryable: false`. This is a policy suspension, not an outage — retrying will not succeed until re-enabled via the changelog. Non-template sends are not affected.

See `docs/decisions/2026-08-30-suspend-send-template.md` for the reason and restoration gate.

### D13 delivery guarantee

Dispatch is at-most-once per `Idempotency-Key`:

- A retry with the same key and same body replays the stored response — no second provider call.
- A concurrent retry while the first is in flight answers `idempotency_in_progress` (retry after backoff).
- A takeover that finds an `intended` row never calls the provider; it marks `indeterminate` and returns `idempotency_indeterminate`.

An `indeterminate` answer means the message **may have been delivered**. Do not retry with a new key. Reconcile by listing the conversation's messages (`GET /v1/conversations/{id}/messages`) and matching `provider_message_id` to the wamid from the accepted send, or wait for `message.accepted` (payload `message_id` = wamid). The `biz_opaque_callback_data` reconciliation channel can promote some `indeterminate` records to `reconciled_sent`, but it never makes an indeterminate safe to resend — silence is absence of evidence, not evidence of absence.

This is **not exactly-once**. The PRD's exactly-once phrasing is superseded by `docs/decisions/2026-09-01-d13-dispatch-state-machine.md`.

### QR-mode and capability matrix

`evolution_qr` (Direct QR) supports no messaging type. The full matrix is in `docs/api/openapi.yaml` `POST /v1/messages` description (Phase 9.2 block).

Reference: `supabase/functions/partner-api/v1/messages.ts`, `docs/api/openapi.yaml` paths `/v1/messages` and `docs/decisions/2026-09-01-d13-dispatch-state-machine.md`.

## Media

### Upload then reference

`POST /v1/media` stores bytes; `POST /v1/messages` references them by `media_id`. No send path accepts an external URL. Requires `Idempotency-Key`. Scope `media:write`.

Accepts `multipart/form-data` with `file` part, or JSON with `data` (base64 or `data:` URL) plus optional `filename`/`mime_type`. Declared `mime_type` is checked against sniffed bytes — mismatch is refused, not corrected.

On success `201` with `{id: media_…, mime_type, kind, size_bytes, created_at}`. No partner-facing URL is returned.

`GET /v1/media/{id}` returns metadata only. Workspace-scoped: a `media_id` from another workspace answers `resource_not_found`. Scope `media:read`.

### Allowlist and size limits

The accepted types and per-kind byte limits are defined in `supabase/functions/_shared/partnerMediaSniff.ts` and pinned in `docs/api/openapi.yaml` `POST /v1/media` description and `docs/decisions/2026-09-01-d10-media-control-matrix.md`. Cite the document for the numbers — the code is the one place they are enforced.

Exceeding the limit → `payload_too_large` 413 `retryable: false`. Sniffed type outside allowlist → `unsupported_capability` 422.

### Scan states

Every `media_id` carries `scan_state`:

- `pending` → `media_pending` 409 `retryable: true` — retry the same request shortly.
- `rejected` → `media_rejected` 422 `retryable: false` — upload different bytes.

Today every partner upload lands `available`; the states exist for when a scanner is introduced (`docs/decisions/2026-09-02-phase9-rich-media.md`).

Reference: `supabase/functions/partner-api/v1/media.ts`, `docs/api/openapi.yaml` `POST /v1/media`.

## Publishing

### Posts — only API-created posts are addressable

`POST /v1/posts` creates a post for explicit `targets: [acc_…]` (one workspace, non-empty, no WhatsApp targets). Optional `scheduled_at` must be ISO-8601 with explicit offset. Quota may refuse with `quota_exceeded`. Requires `Idempotency-Key`. Scope `posts:write`.

A post created in the Postora UI answers `resource_not_found` on every `/v1/posts` route, permanently and by design (`docs/decisions/2026-09-02-phase8-posts-scheduling.md` Decision A).

- `GET /v1/posts/{id}` — fetch the post. Scope `posts:read`.
- `GET /v1/posts/{id}/status` — per-target `platform_posts` rows with `provider_post_id`/`provider_post_url`. Scope `posts:read`.
- `POST /v1/posts/{id}/schedule` — set `scheduled_at` (pending or scheduled only). Scope `posts:schedule`.
- `DELETE /v1/posts/{id}/schedule` — clear schedule, parks as `pending`. Scope `posts:schedule`.

There is no `POST /v1/posts/{id}/publish` yet. Publish by scheduling; `process-scheduled-posts` picks up rows matching `status IN ('pending','scheduled') AND scheduled_at IS NOT NULL AND scheduled_at <= now()` and publishes them.

### Events

`post.scheduled` is certified and emitted by a database trigger for every schedule writer (`docs/decisions/2026-09-02-phase8-posts-scheduling.md`). `post.published`/`post.failed` have a live producer but remain uncertified until observed in production. Unschedule emits no event.

## Connectors and tools

A **connector** is a system a Postora workspace has wired up — a database, a store, a CRM, a chat workspace. A **tool** is one connector as it is configured and named in Postora, with the accounts it is available to. The Postora AI agent calls tools while it answers customers; these two routes let your own code call the same tools, without a model in the loop.

### What a key can see and run

Visibility is decided by the same resolver the agent uses. A tool is reachable by a key when it resolves for an account **bound to that key** — either configured for that account, explicitly shared with it, or shared across all of its owner's accounts. Nothing else grants access, so what `GET /v1/connectors` lists is exactly what `POST /v1/tools/execute` accepts.

Tools marked admin-only in Postora are never listed and never executable through the API. Those are reserved for a verified admin inside a conversation, and a key is not a person.

### `GET /v1/connectors`

Scope `connectors:read`, D7 class A. Returns every reachable tool, de-duplicated by `tool_id` — a tool shared with two bound accounts is one entry, not two. The listing is not paginated (it is bounded by the key's own bindings) but still returns `next_cursor: null`, so one paging loop works against every listing.

Each entry carries `tool_id`, `name`, `connector_type`, `auth_strategy`, `category`, `scope`, `social_account_id`, `connection` and `usage_30d`.

`auth_strategy` is `manual_credentials` for a connector configured with credentials held in Postora, or `composio_oauth` for one authenticated through a connected third-party account. Only the second kind has a `connection`, and it shows the connection's `status` and its human `external_account_label`. Provider account identifiers are never returned.

`usage_30d` counts connector calls in the key's **workspace** over the last 30 days, from every door — the AI agent, this API, the connector test button, publishing — not only this key's calls. `failures` counts calls that failed or timed out; a refusal is Postora declining to make the call and is not counted as a connector failure. `p50_latency_ms` is the median over calls that recorded one, and is null when none did. A workspace past 10 000 calls in the window is summarised over its 10 000 most recent calls.

### `POST /v1/connectors/{type}/connect-link`

Scope `connectors:manage`, D7 class C, `Idempotency-Key` required. Starts an authorisation flow for one connector type and returns `{connection_id, redirect_url, expires_at}`.

`{type}` must be a connector type that authenticates through a connected third-party account. A native connector type and an unknown type both answer `connector_type_not_connectable` (400).

The connection is created for the key's own workspace; there is no way to name another. The optional body field `social_account_id` records the account you intend it for — it does not change what is minted, and an account outside the key's binding answers `resource_not_found`.

`connection_id` is not usable when it is returned. A human must open `redirect_url` and finish authorising before `expires_at`. Composio's hosted page ends on its own "Successfully connected" screen and does not redirect anywhere, so nothing on the browser side signals completion.

**Current limit:** a connection minted through this route is activated only when Postora reconciles it against Composio — today that happens when the same workspace's connection is completed from the Postora app (which polls `composio-connect/finalize`), not on a schedule. Until a partner-side finalize exists, treat a `connect-link` connection as complete only once `GET /v1/connectors` lists it with `status: "active"`; an `initiated` row that is never reconciled expires after one hour.

A retry with the same key and body returns the stored link. A mint that **failed** is not stored, so the same key becomes usable again once its claim lease expires; until then a retry answers `idempotency_in_progress` (409, retryable). Use a new key if you need a link sooner.

### `POST /v1/tools/execute`

Scope `tools:execute`, D7 class C, `Idempotency-Key` required. Body `{tool_id, social_account_id, capability, parameters}`; ids are UUIDs from `GET /v1/connectors`, not prefixed ids. `social_account_id` is required even for a tool shared across accounts — it is what authorises the call.

`capability` must be one the connector declares. For a connector authenticated through a third-party account it is the provider's own action name, such as `SLACK_SEARCH_MESSAGES`. Anything else answers `connector_tool_not_allowed` (403).

A capability that **changes data** in the connected account additionally requires the tool's owner to have enabled writes in Postora. A key cannot widen that: without it the answer is `connector_write_not_allowed` (403). Connectors configured as plain webhooks have no typed capability contract and are not executable here.

Success is `200 {ok: true, data, request_id, latency_ms}`, where `data` is what the connector returned, unchanged.

### Errors and what to do about them

`tool_not_found` (404) is the single answer for an unbound account, an unknown `tool_id`, a malformed id, a tool that does not resolve for that account, and a tool whose connection belongs to another workspace. It is deliberately non-enumerable — do not read it as "wrong URL".

`connection_inactive` (409) means the tool's connection is not `active`. Nothing changes on its own; someone reconnects it in Postora, or you mint a new connect link.

`connector_unavailable` (503, retryable) means the connector service is not configured for this deployment, or could not be reached.

`tool_execution_failed` (502, retryable) means the connector ran and reported failure. The body carries the code only — provider messages never pass through. Retrying with the **same** `Idempotency-Key` returns the stored 502 rather than executing again.

`tool_execution_timeout` (504) means the 20-second execution budget expired, and the outcome is **unknown**: the call may have taken effect. Retrying with the same key answers `idempotency_indeterminate` (409) on purpose. Reconcile in the connected system rather than executing again.

### Metering

Every call is recorded against the workspace's connector usage, including every refusal against a tool the key can see; those show up in `usage_30d`. A `tool_not_found` refusal is recorded too but cannot be attributed to a listed tool, so it never appears there. Tool execution consumes no monthly message quota, and its `partner_api_usage` row is non-billable.

Reference: `supabase/functions/partner-api/v1/connectors.ts`, `supabase/functions/partner-api/v1/tools.ts`, `docs/api/openapi.yaml`.

## Social Accounts

### Binding model

A partner key sees only the social accounts bound to it (`partner_api_key_accounts`, spec D4). The binding may be a strict subset of the workspace's accounts. There is no "list everything in the workspace".

### List and get

- `GET /v1/accounts` — the bound accounts. Not paginated; a too-large binding is refused with `invalid_request` rather than truncated. Scope `accounts:read`. D7 class A.

- `GET /v1/accounts/{id}` — one bound account. An id outside the binding — or a malformed id — answers `resource_not_found` indistinguishably, so the binding is non-enumerable (D11). Scope `accounts:read`. D7 class A.

Every other `/v1` read is scoped to exactly this set. Naming an unbound `account_id` (e.g. `?account_id=` on `GET /v1/conversations`) answers `resource_not_found`, never a distinct forbidden code.

All bound accounts are listed. WhatsApp accounts expose conversations and messages; publishing-only targets have no conversation message history.

Example:

```bash
curl -H "x-postora-key: pk_live_REPLACE_ME" \
  https://api.postora.cloud/functions/v1/partner-api/v1/accounts
```

## Versioning and Compatibility

Per PRD §43. This page is the compatibility policy before GA.

### What is additive and needs no migration

- New routes under the same major prefix (`/v1`).
- New optional request fields (nullable, defaulted).
- New values inside `details` or new webhook event types (on the certified list).
- New entries in `meters` arrays.

A client must tolerate unknown fields and unknown enum strings in extensible places. The OpenAPI document is additive-only under this rule.

### What is breaking

- Removing a route or field.
- Narrowing a type (`string` → enum, optional → required).
- Removing an enum value.
- Repurposing a field's semantics without a new major.

A breaking change requires a new major path prefix (`/v2`). Webhook schemas follow the same rule — a breaking payload change ships under a new event version or new major.

### Deprecation window

A feature marked `Deprecated` in `deprecations.md` carries `replacement`, `deprecation_date`, `planned_removal_date`, and `migration` steps. No silent repurposing — behavior changes are announced in `changelog.md` first.

### How the drift gate enforces it

## Deprecations

Each entry records: `replacement`, `deprecation_date`, `planned_removal_date`, `migration`. No removal without a migration path announced in `changelog.md`.

### Frozen action alias — `POST /functions/v1/partner-api`

- **Status:** Frozen (D1). Still served. No new actions are accepted on it.
- **Replacement:** REST `POST /v1/messages`, `GET /v1/templates`, and `GET /v1/usage` as applicable.
- **Deprecation date:** Not deprecated — frozen. The alias is frozen (D1) and its sunset has three conditions that are not yet met; no date.
- **Planned removal:** No date.

Do not build new integrations against the alias.

### Legacy `whatsapp:*` scopes

- **Status:** Frozen at current capability, not issuable to new keys (D3).
- **Affected values:** `whatsapp:template.send`, `whatsapp:templates.read`, `whatsapp:webhooks.manage` (the last authorises nothing).
- **Replacement:** `messages:send`, `templates:read`, `webhooks:manage` respectively (`whatsapp:webhooks.manage` has no replacement — it never authorised anything).
- **Deprecation date:** deprecated when the generic vocabulary shipped; date not recorded.
- **Planned removal:** No date — existing keys remain valid at frozen capability until their operator reissues them.
- **Migration:** Ask the operator to reissue the key with generic scopes.

Reference: `supabase/functions/_shared/partnerScopes.ts` `LEGACY_SCOPES`.

Format follows Keep a Changelog. Every entry that changes a partner's integration states what they must do.

### Unreleased

#### Added
- `GET /v1/connectors`, `POST /v1/connectors/{type}/connect-link`, `POST /v1/tools/execute` — the connectors and tools surface (`supabase/functions/partner-api/v1/connectors.ts`, `tools.ts`; see `connectors.md`). **Must do:** scopes `connectors:read` / `connectors:manage` / `tools:execute`; send `Idempotency-Key` on both POSTs; treat `tool_not_found` as non-enumerable, and `tool_execution_timeout` (504) as an unknown outcome to reconcile, never to re-execute.
- Generic scopes `connectors:read`, `connectors:manage`, `tools:execute`. **Must do:** ask the operator to reissue the key if you need them; no existing scope satisfies them.
- Error codes `connection_inactive`, `connector_tool_not_allowed`, `connector_type_not_connectable`, `connector_unavailable`, `connector_write_not_allowed`, `tool_execution_failed`, `tool_execution_timeout`, `tool_not_found`. **Must do:** branch on `code` and honour `retryable`, as with every other code.
- `GET /v1/usage` — monthly meters `reserved`/`confirmed`/`indeterminate`/`charged` (`supabase/functions/partner-api/v1/usage.ts`). **Must do:** scope `usage:read`.
- Environment-bound keys (`pk_test_` staging prefix, `environment` on every key, a staging key never authenticates against production) (`supabase/functions/_shared/partnerApiKeys.ts:12`). **Must do:** use `pk_live_REPLACE_ME` against production only.
- Developer documentation under `docs/developer/` — no contract change.
- Generated Postman collection and environments (`docs/api/postman/`, `scripts/generate-postman.ts`). **Must do:** use `{{baseUrl}}` + `/v1` paths; credentials remain `pk_live_REPLACE_ME` placeholders.

#### Changed
- `POST /v1/messages` 2xx bodies now carry `request_id` (`supabase/functions/partner-api/v1/messages.ts:50`). **Must do:** correlate via `request_id`.
- Every `/v1` replay now carries `Idempotency-Replayed: true` (`supabase/functions/_shared/partnerApiIdempotency.ts`, `messages.ts:59`). **Must do:** branch on header if you need replay detection.
- `POST /v1/media` now documents the `Idempotency-Key` it always required (`docs/api/openapi.yaml:335`). **Must do:** send the header.
- A `/v1` 429 now carries `X-RateLimit-Limit`, `X-RateLimit-Remaining: 0` and, when the limiter supplied a reset, `X-RateLimit-Reset` and `Retry-After` (`supabase/functions/_shared/partnerApiMetering.ts` via `authenticated.ts`). **Must do:** back off `Retry-After`; handle its absence.
- `POST /v1/messages` and `GET /v1/templates` are now described in the OpenAPI contract (`docs/api/openapi.yaml:443`, `546`). No behavior change — contract now matches code.

### 1.0.0 — 2026-09-02

Live today on `main`: base URL `https://api.postora.cloud/functions/v1/partner-api`, all routes under `/v1`.

#### Added
- `GET /v1/accounts`, `GET /v1/accounts/{id}` — bound accounts (D4, D11). **Must do:** scope `accounts:read`, filter by returned `acc_` ids only.
- `GET /v1/conversations`, `GET /v1/conversations/{id}`, `GET /v1/conversations/{id}/messages`, `GET /v1/messages/{id}` — WhatsApp reads, cursor-paginated on `(last_message_at,id)` / `(timestamp,id)` with `next_cursor`. **Must do:** `conversations:read` / `messages:read`, loop on `next_cursor`.
- `POST /v1/media` (`Idempotency-Key`), `GET /v1/media/{id}` — byte-sniffed allowlist, per-kind limits, workspace-scoped. **Must do:** `media:write`/`media:read`, reference by `media_id` only.
- `POST /v1/messages` (Idempotency-Key, D13 dispatch boundary), media types `image|video|audio|document` via `media_id`, capability matrix at the door (Phase 9.2), scan-state refusals `media_pending`/`media_rejected` (Phase 9.3). **Must do:** `messages:send`, handle `unsupported_direct_qr`, `media_pending`, D13 indeterminate reconciliation.
- `GET /v1/templates` — proxied from Meta, `next_cursor` always `null`. **Must do:** `templates:read`.
- `POST /v1/posts`, `GET /v1/posts/{id}`, `GET /v1/posts/{id}/status`, `POST/DELETE /v1/posts/{id}/schedule` — posts surface (Phase 8). Only API-created posts are addressable. **Must do:** `posts:write`/`posts:read`/`posts:schedule`, publish by scheduling.
- `GET /v1/webhooks`, `POST /v1/webhooks`, `GET/PATCH/DELETE /v1/webhooks/{id}`, `POST /v1/webhooks/{id}/rotate-secret`, `POST /v1/webhooks/{id}/test` — webhook substrate with HMAC `sha256=<hex>` over `<timestamp>.<body>`, headers `X-Postora-Event`/`X-Postora-Event-Id`/`X-Postora-Timestamp`/`X-Postora-Signature`, ladder `1m/5m/30m/2h/6h`, 6 attempts, 24h rotation overlap, certified events `webhook.test`, `message.received/accepted/delivered/read/failed`, `account.reauthorization_required`, `post.scheduled`. **Must do:** `webhooks:read`/`webhooks:manage`, verify signature as documented, dedupe on `X-Postora-Event-Id`.

#### Changed
- Error envelope carries `error.retryable` typed retry verdict (D2). **Must do:** retry only when `retryable: true`, never on status family alone. Divergence from PRD documented.

#### Deprecated
- Action alias `POST /functions/v1/partner-api` — frozen, no new actions (D1).
- Scopes `whatsapp:template.send`, `whatsapp:templates.read`, `whatsapp:webhooks.manage` — frozen, not issuable to new keys (D3).

#### Security
- Keys stored as SHA-256 hash, prefix check before lookup, non-enumerable 401, signed storage URLs, per-hop webhook URL revalidation.
