## Persistence decision

**Published edits.** Keep Google authoritative. Store draft, baseline and edit revision for the active selection in memory only. Use Google item ETag plus owner-scoped fresh reads for concurrency; do not introduce an edits table, metadata cache, token column or local replica. An opaque revision can be a deterministic digest over version, owner, account, channel, video and actual provider ETag, recomputed server-side. It grants no authority by itself. An uncertain update only needs another owner-bound read and explicit review. A DB lock cannot repair a provider that ignores conditional writes.

**Uploads.** Reuse `posts.id` for stable submit identity, existing `platform_posts` target/result and `response_data` for small additive receipts, existing private native upload sessions for offsets and leases. Preserve the stored attempt's native initialization body/options on resume. Keep IDs and status enums compatible with existing readers. Put managed dispatch marker and follow-up evidence under a versioned YouTube namespace, bound to target and attempt. Store only outcome, reason, time and confirmed provider ID. No raw video data, URLs, credentials, request bodies, signed URLs or comment text. Missing old evidence renders “Not recorded”.

**Migration trigger and gate.** No unconditional schema migration. Before implementing managed execute, prove in isolated concurrent transactions that an existing target row can be created/claimed exactly once for a given owner/post/account, that only the active owner-bound attempt can transition from definitely-unsent to dispatch-possible and to confirmed, and that an old worker, timeout or generic retry cannot erase that marker or create a second row. Verify every reader, including manual retry and scheduled re-claim. A read followed by an ordinary upsert, a connector call log, or a native session reused for a managed tool is insufficient. Also prove that result updates preserve unrelated JSON keys and cannot lose a receipt. If existing DB primitives cannot enforce these transitions, include **one additive service-only RPC migration** in this delivery. Reuse target rows if structurally unique. If uniqueness across attempts is not enforceable on that row, add a private operation table with unique owner/post/account logical intent, bound FKs or owner joins, attempt fence, state and receipt. Validate preexisting data before adding constraints. Pin search_path, revoke PUBLIC/anon/authenticated execute, grant service role only, enable RLS/no browser access and test isolation. Apply and validate migration before dependent code becomes reachable. Do not add a second native upload-session implementation. Hold managed execute until duplicate safety is proven.

## Rollout, private fixture and rollback

1. Independent plan debate first. Resolve material objections in both docs. Confirm stage-wide server activation mechanism and a single authorized test owner/channel/video with private visibility. Confirm whether a separate disposable private upload (and which provider) is authorized. Neither the plan nor a review approves a live write.
2. Build the entire candidate behind server-side controls defaulting to disabled for new edit and candidate-only writes. Restrict fixture rollout by verified owner/account. Client feature detection preserves read-only browse against old backend. Validate both old/new-client combinations. Keep any safety fences across flag changes. Do not let a disabled marker send a managed target back into its previous unguarded retry path.
3. Heavy review and approvals, snapshot ahead of any migration, record schema verification and compatibility with old workers. Follow [self-hosted runbook](../runbooks/deploy-edge-function.md). The main-branch Edge sync may run every two minutes and the frontend deploys separately. Coordinate schema/flags **before merge**. Deploy staging in isolation, verify SHA256/boot probe for each changed function and checks against the self-hosted URL. Only Waleed authorizes production/server changes. A merge or a healthy unrelated function does not establish rollout.
4. After fixture authorization, record private video ID, channel binding, privacy and relevant original writable values securely for restoration. Open in library, change one reversible title suffix, save, reread same ID, compare untouched fields and private visibility. On the same disposable fixture use two baselines, verify stale write is rejected at provider even if the competing change lands after pre-read. Check no second video exists. Restore the title using latest revision, reread and compare to baseline; stop for owner review if another editor changed it. Exercise visibility widening only with fakes. Never turn a real fixture public/unlisted to test confirmation.
5. For a separately authorized upload, submit one small owned file with explicit private visibility and notifications off on an eligible native channel. Record returned ID, effective privacy and separate follow-up results; simulate lost acknowledgements offline. Only exercise managed live upload if its own fixture, possible notification behavior and provider restrictions are explicitly approved. No blind retry or deletion on uncertainty. Cleanup requires owner's named fixture policy. Keep sanitized receipts (candidate SHA, request IDs, timestamps, comparison results), never access tokens or private media in PRs.
6. Stop promotion on wrong channel/ID, privacy drift, lost sibling, accepted stale ETag, mutable unknown field, ambiguous managed replay, missing ownership predicate, missing follow-up evidence presented as success, or binding/rollout drift. Disable new writes at server and hide action via capabilities. Preserve browse, existing session evidence and reconciliation. Drain or park in-flight attempts, retaining possible-send markers. Revert compatible frontend/Edge candidate via approved deployment path, keeping additive schema/receipt readers until all in-flight work is reconciled. Never roll back by replaying uploads or blindly restoring someone else's metadata. Confirm baseline browsing, private visibility, same-ID reads and no repeated execution. Record affected request IDs and the owner's next decision.

## Decisions for the independent debate

- Verify the real item ETag works for this exact projection and conditional PUT. If evidence is unavailable, keep the feature disabled pending the authorized private proof.
- Review the proposed private Create Post default and managed unsupported-option behavior for old versus newly requested options. Preserve explicit prior user choices.
- Choose existing atomic target primitives or the conditional additive migration after the race test. Reject a design that permits managed duplicate execution or loses an unknown receipt after rollback.
- Confirm fixture, operational authority and rollback owner before scheduling any live validation. No implementation or deployment is part of this planning handoff.
