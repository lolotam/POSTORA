## 2. Server-owned eligibility

### One policy, independently approved populations

Keep `collection_instagram_insights_enabled` as the existing master kill switch. Add one private, non-`feature_` `app_settings` key, `collection_instagram_rollout_policy`, with this exact versioned shape and default:

```json
{
  "version": 1,
  "owners": { "mode": "off", "account_ids": [] },
  "competitors": { "mode": "off", "targets": [] }
}
```

Each mode is exactly `off|allowlist|all`. Owner entries are internal `social_accounts.id` UUIDs, never provider IDs, usernames or user UUIDs. Competitor entries are exactly `{ "watchlist_id": "<uuid>", "viewer_social_account_id": "<uuid>" }`: an owned watchlist identity and one explicitly approved viewer. Both are database IDs, with their same-owner relationship checked structurally on every use. The placeholders illustrate a shape; no real identifiers belong in these public documents.

- `off` admits no targets. Lists may be retained for rollback bookkeeping but confer no access.
- `allowlist` admits only exact listed IDs. A competitor must use its pinned viewer; no automatic substitution on failure. Owner eligibility does not grant competitor eligibility, and viewer permission does not grant owner-insights collection for that viewer.
- `all` admits all otherwise eligible owned targets of that kind, including future targets. It does not bypass active/reauth, trusted capability, credential, quota-management, due-date or lease rules. Lists must be empty in `all` to prevent ambiguous pin semantics. Competitor `all` uses the existing deterministic, same-owner, trusted Page-linked selector restricted to usable protected bindings; never another owner's account.
- Both lists are capped at 500 entries; UUIDs are validated/canonicalized, duplicates and unknown keys rejected. A competitor allowlist names **one pinned viewer per watchlist**: two entries with the same `watchlist_id` are a duplicate, even with different viewers, so attach and permits never have a second viewer to fall back to. Empty allowlist admits nobody. Malformed either section invalidates the entire policy. Adding an entry never removes an existing grant; removing an entry never widens access. There is no “empty means all” or “missing viewer means choose anyone” interpretation.

Effective permission is the intersection of master-enabled, valid policy membership and live target/credential eligibility. A missing policy means off; a failed/malformed read means configuration unavailable, never off-as-success or all. Master missing/false refuses before touching new rollout/job/credential schema. Master malformed/unreadable refuses with `settings_unavailable`. Neither missing setting nor a failed lookup may enable work. Migrations insert default policy only if absent and never overwrite an operator's existing value.

Reads and writes go through two service-only RPCs. `get_instagram_collection_rollout_policy()` returns the canonical policy and its fingerprint: the hex SHA-256 of the canonical JSON (keys sorted; owner UUIDs lower-cased and sorted; competitor entries lower-cased and sorted by `(watchlist_id, viewer_social_account_id)`). Canonicalization never repairs a policy: a duplicate owner ID or a repeated competitor `watchlist_id`, like any other malformed value, makes both RPCs fail closed (RC-01) for admission and for any edit of that value. Recovery from a malformed or unparseable **stored** value is the one exception, and it never admits anything: the getter then returns `status = 'malformed'` with a fingerprint of the raw stored text, and the setter accepts that fingerprint as the expected value only to replace the whole value with a fully valid policy, under the same row lock and audit. Collection stays refused until the replacement commits. `set_instagram_collection_rollout_policy(p_expected_fingerprint text, p_policy jsonb, p_actor text, p_approval_ref text)` locks the `app_settings` row, recomputes the stored policy's fingerprint, and refuses with a typed `policy_stale` unless it equals `p_expected_fingerprint`. That parameter is only a concurrency token compared against the server's own recomputation; it is never stored or trusted as the audit fingerprint. The RPC then validates and canonicalizes the new value and commits the policy change audit in the same transaction. The existing admin `app_settings` upserts are last-write-wins, so they must not write this key: a trigger refuses any other write to it. A stale edit after a rollback therefore cannot restore a removed allowlist member. Ordinary authenticated and anonymous clients cannot read or write the key or call either RPC; test actual table policies and grants. No UI or general-purpose new configuration endpoint is in scope. An admin JWT may invoke a privileged drain but cannot bypass the policy. The audit row holds the timestamp, the server-computed fingerprints before and after, and the actor. A service-role session has no verified user, so `p_actor` (the operator) and `p_approval_ref` (the Task 11 approval it implements, such as D2) are required and must be nonblank after trimming and at most 200 characters (null, empty and whitespace-only values are refused, and RC-17 tests each); they are recorded as **asserted**, not verified; the approval record in Task 11 is what proves who approved. Never accept an eligibility boolean supplied by a caller.

### Enforcement sites

R1 adds a single SQL policy evaluator used by the existing enqueue/claim/fence routines. TypeScript consumes typed decisions; it does not independently decide membership from copied arrays.

1. **Owner and service enqueue:** resolve real owner/target first, then evaluate eligibility before throttle consumption, force generation changes or job insertion. Foreign/missing targets remain indistinguishable. Every service batch element checks `(owner, target kind, target id)`; a forged owner cannot obtain a usable job.
2. **Due discovery:** restrict owner and competitor target selection to eligible rows before page limits. A one-account pilot cannot scan the first 500 excluded jobs forever and starve its one eligible job.
3. **Claim:** apply eligibility to every candidate query, including reserved fresh work, recovery discovery and finalization, then recheck under existing parent→job locks in `ig_collection_try_claim_job`. Old queued/retry/partial jobs for excluded targets stay unclaimed; their attempts, generation and freshness are unchanged. Master off prohibits direct service RPC claims too.
4. **Viewer binding:** `attach_instagram_collection_job_viewer_context` checks target admission, exact pinned viewer in allowlist mode, live same-owner Page-linked capability and protected User binding. Apply this in SQL, not only in `listViewerCandidates`.
5. **Before each provider HTTP request:** a service-only `authorize_instagram_collection_provider_call(p_job_id,p_claim_token,p_job_generation)` derives scope from the live fenced job, checks current policy and captured credential generation, and returns a typed nonsecret permit/refusal. Call it inside the actual transport boundary, including retries and cursor/media requests, with no permit caching between requests. Failure or timeout means no provider request. Competitor permit includes the bound viewer identity, never a caller-selected substitute.
6. **Writes:** extend the common fence used by progress, snapshots, direct credential reads and completion, plus competitor v1/v2 result paths, to reject currently excluded targets/viewers. Preserve generation/lease/connection checks and lock order. Provider failure health writes must also respect the job's captured authority. Rollout refusal never marks target unavailable, revokes a credential, or advances success.

For an allowlisted account/target, SQL joins still prove ownership, Instagram platform, activity and capability. A readable account UUID is not authority. Direct SQL access by trusted service role remains structurally scoped; ordinary roles cannot execute worker/configuration primitives. New definer routines have fixed `search_path`, explicit PUBLIC/anon/authenticated revokes and narrowly necessary grants. Internal helpers are not independently callable by service_role.

### Refusal, audit and concurrency semantics

Introduce the stable reason `collection_not_eligible`; preserve `collection_disabled`, `settings_unavailable`, `protected_credentials_required` and existing auth/not-found reasons. Owner/competitor intake maps a valid but excluded owned target to HTTP 403, unavailable configuration/authority to 503, and cross-owner/missing to the same 404. Successful existing enqueue/status payloads remain unchanged. Add a strict refusal union to affected SQL receipt parsers; do not turn a refusal object into a successful job. Force refusal consumes no 15-minute throttle slot.

The new provider-permit RPC returns exactly `{allowed:true,job_id,target_kind,target_id,viewer_social_account_id,job_generation,credential_generation,policy_fingerprint}` or `{allowed:false,reason_code}`. `viewer_social_account_id` is always present: `null` for an owner permit and the approved viewer's `social_accounts.id` UUID for a competitor permit; any other combination is a malformed receipt. Every identity/generation is derived from and checked against the fenced job; no token is returned. A malformed/extra-key receipt, mismatched identity or unknown reason is unavailable, never permission. The fingerprint is audit evidence, not a reusable authorization token. Existing enqueue RPCs add `{refused:true,reason_code}` for definite rollout refusals (per item for a service batch); their accepted count excludes refused items. Existing claim SETOF results remain job rows only, with empty exclusion outcomes audited in SQL. Exceptions retain established SQLSTATE mapping and separate Edge audit.

Claims may return zero jobs when policy excludes all candidates, but must write a sanitized aggregate refusal event distinguishing exclusion from an empty queue. Configuration/read errors must raise a typed failure, not return an empty set. SQL normal refusals write a `system_logs` row in the same committed transaction and return a refusal/empty claim result; **inserting a log then raising an exception does not persist the log**. Unexpected SQL errors are audited by the Edge adapter in a separate bounded call after rollback. Existing HTTP refusals use the existing `system_logs` sink. If audit fails, stop work, emit a sanitized fallback operational error and report audit failure; never report a stored row that did not commit.

Record event, action, safe reason, verified actor where available, owned target/job IDs where appropriate, policy fingerprint and counts. No raw policy lists, tokens, headers, provider URLs, claim tokens or provider payloads. Broad scans use one bounded aggregate event per invocation, not thousands of excluded-row events. Auth/method/body refusals are logged; OPTIONS preflight is not work. Keep DB/HTTP audit correlation so a valid refusal is not mistaken for silent no-work.

A configuration change cannot retract an HTTP request already authorized or in flight. Define the authorization instant as the last SQL permit immediately preceding the request; recheck each subsequent request and each result write. A removal/off change observed before that instant produces zero calls; a change after it may leave one already-authorized request per active transport in flight, whose now-ineligible result cannot persist. No new parallel transport is introduced. Rollback must settle these bounded calls and leases before claiming complete cessation or re-enabling. Do not hold database locks across HTTP. Two-session tests prove both interleavings; do not promise physically atomic cancellation across SQL and Meta.

## 4. Owner daily enqueue HTTP dispatcher and durable continuation

Add `POST /functions/v1/instagram-insights-sync` with **exact body** `{"action":"enqueue-daily"}`. Reject unknown fields, caller-selected owner/account/date/cursor/limit/force, invalid JSON and >4 KiB bodies. OPTIONS and method rules remain existing conventions. Reuse owner drain's authentication: exact constant-time cron-secret/service-key match, or verified authenticated admin with strict server role lookup. Ordinary user, anon and forged service claims are refused. `enqueue`/`status` retain own-only bearer RPC authority, including admin-own-only; service auth cannot impersonate them.

The dispatcher enqueues; it makes **zero Meta/Apify calls**. It uses database-selected current Asia/Kuwait capture day, normal idempotent jobs, and never forces completed work or spends the owner's accepted-request throttle. Responses are:

- `202`: `{"action":"enqueue-daily","captured_on":"YYYY-MM-DD","sweep_status":"pending","enqueued":N,"has_more":true}` when committed progress remains.
- `200`: same fields with `sweep_status:"completed"`, `has_more:false` when the bounded SQL page proves no eligible unqueued target remains; N may be zero on repeat/no-work.
- `503`: typed disabled/configuration/unavailable/indeterminate response, never manufactured completion. A missing or malformed mutation reply is indeterminate; do not retry it in the same invocation. `enqueued` is this call's newly inserted rows, not successful collections.

### R2 sweep contract

Create service-only `instagram_collection_enqueue_sweeps`, keyed by `(target_kind,captured_on)`, with pending/completed/expired state, started/updated/completed timestamps and nonsecret progress counts. RLS enabled, no browser table access. Add `enqueue_instagram_collection_daily_page(p_target_kind text,p_start boolean DEFAULT false) returns jsonb`, service-only, fixed search path. It accepts `p_target_kind` only from the closed set `owner|competitor` (the collection-job contract's own set) and returns `{ok:false,reason_code:"invalid_target_kind"}` before creating or locking any sweep for any other value. Its receipt is exactly the union `{ok:true,target_kind,captured_on,sweep_status,enqueued,has_more}` (`sweep_status` is `pending`, `completed`, or `none` — the last only for `p_start=false` when no pending current-day sweep exists, with `enqueued:0,has_more:false`; a drain treats `none` as no work and proceeds to claim without error) or `{ok:false,reason_code}`, where `reason_code` is `invalid_target_kind` or one of the canonical admission refusals in §2 "Refusal, audit and concurrency semantics"; an unknown code or shape is unavailable, never success. `invalid_target_kind` is a caller input error, not an admission refusal: the RPC itself creates and locks no sweep and writes one bounded, sanitized input-error `system_logs` row (classified separately from admission refusals), so a direct service call or a miswired adapter is never mistaken for silent no-work and adapters do not log it a second time; admission refusals keep their committed SQL audit row. It has no owner/date selector; constants cap one page at 25 owners or 50 competitors.

The RPC serializes the kind/day sweep row, atomically selects eligible due targets **without a job for the current capture day**, inserts normal jobs using the canonical admission checks, updates counts and returns the bounded receipt. Use the existing natural job key and conflict handling. The anti-join is the continuation mechanism: successfully enqueued rows disappear from the next candidate page, so there is no volatile process cursor to lose. Deterministic indexed ordering and bounded lock/statement timeout are required. Preserve competitor `next_retry_at` weekly gate; a force API remains a separate authorized path. An ineligible target cannot block a later eligible target.

`p_start=true` starts or reopens the current day's sweep, permitting an explicitly invoked dispatcher to include newly approved targets without resetting existing jobs. `p_start=false` resumes only an already pending current-day sweep. It never starts collection merely because a drain ticks. Each drain spends at most one enqueue page within its existing total 40-second budget, then claims at most its existing 25/50 jobs; if insufficient time remains, it logs deferred work. No separate unbounded waitUntil/self-HTTP loop. Every subsequent tick resumes until `has_more=false`, including populations larger than 25, 50 and 1,000.

On Kuwait day rollover, unfinished prior sweep is recorded expired with incomplete evidence; start only a current-day sweep via the daily dispatcher. Never fabricate historical follower observations or silently mark an unfinished sweep completed. Existing old job recovery and owner lag repair still operate through their own claim rules. New targets after a completed sweep wait for another explicit start or the next daily schedule. Removed/reapproved targets are always checked against current policy, irrespective of sweep state.

For competitors, retain existing accepted `mode:"enqueue-daily"` validation and legacy cursor-based caller behavior, with R1 filtering applied. Add strict `dispatch:"durable"` to that service mode as a distinct schema branch, with no cursor/limit fields; it uses the same R2 mechanism and bounded receipt. C1 always sends `{"mode":"enqueue-daily","dispatch":"durable"}`. This preserves existing consumers without making cron depend on reading `nextCursor`. Competitor `mode:"all"` resumes only its pending sweep before draining. No daily dispatcher changes the collection policy.

On crash/lost response, the transaction commits page+jobs together or neither; the next call reconciles by persisted state and unique keys. Two dispatchers/drains cannot duplicate jobs, skip a page or force a generation. A budget/DB failure is pending or indeterminate, never “all targets enqueued”. Persist a bounded sweep summary and expose counts only to privileged dispatch callers. Status/report DTOs remain separate.

## 6. Rollout and rollback

Task 11 B–E remains the approval ledger. This spec supplies D1's implementation owner; it does not satisfy D1 or grant production access.

1. With master off and all four jobs inactive, verify additive SQL, ACLs, deployed hashes, route boot and negative fixtures. Keep global credential mode legacy.
2. Under separate D2 approval, set owners to allowlist containing exactly the named account, competitors off, then enable master. Invoke owned enqueue and privileged drain manually. Verify all other accounts have zero collection provider requests, including pre-existing jobs, siblings sharing a grant, and another tenant. OAuth pilot membership is independent.
3. Under separate D3 approval, add exactly one owned watchlist/pinned Page-linked viewer pair. Keep owner population unchanged. Verify no other competitor or alternative viewer is called. Approving a viewer alone never enables its owner collection.
4. Under separate E1 approval, move each population to a specified wider list or all with measured credential exclusions. `all` explicitly includes future otherwise-eligible targets. Under separate E2 approval activate the precise schedules, observe complete daily sweeps/continuations and capacity. Retention remains Task 8/E3.

Rollback first disables the four schedules and master (or narrows only the affected population), records the policy and time, and checks pending/in-flight work. Keep all additive tables, snapshots, success times, protected bindings and operational credentials. New claims/requests stop at the next authorization check; writes after exclusion refuse. Let bounded requests settle and 120-second job leases expire, verifying no new permits before calling the rollback quiescent. If accounting for previously granted permits is uncertain, keep master off and escalate rather than claiming zero in-flight calls.

Use a tested rollout-aware, protected-compatible last-good runtime. A pre-R1 worker lacks the per-request guard and is not a pilot-safe rollback candidate. Do not reset jobs to success, purge queues/history, reverse OAuth protection, remove credentials, flip global credential mode or rely solely on cron inactivity. Re-enable only after a new scoped approval and renewed exclusion proof; retained pending work will be subject to current eligibility.
