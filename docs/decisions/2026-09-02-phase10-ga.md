## 10.1 — the usage counters, and the product decision that gated them

Plan §7 item 2 asked whether quota counts accepted-only or accepted-plus-indeterminate, and
whether it is per key or plan-derived. **Decided: accepted plus indeterminate, per key** — which
is what the code already did (spec §3.1: "quota is consumed by accepted *or indeterminate* sends,
released only on a definite rejection"). The change is accountability, not arithmetic.

`partner_api_keys` now carries `usage_reserved`, `usage_confirmed` and `usage_indeterminate`;
`current_usage_count` stays and is always their sum, because the deployed code reads it. The cap
is enforced against the sum **including reserved**: two concurrent sends that would together
exceed it cannot both pass, because each reserves atomically first. That is PRD §52's
"concurrency-safe" claim, and the E2E chain test proves it on real SQL (scenario 9: quota 5, four
charged, three concurrent sends → exactly one 200).

Two new RPCs move a unit out of `reserved`: `confirm_partner_quota` after the provider accepted,
`indeterminate_partner_quota` when the attempt that made the call cannot say. `reserve` and
`release` keep their signatures. A crash between `markIntentSent` and the confirm leaves a unit in
`reserved` forever: the charged total is right, only the bucket is stale, and nothing reconciles
it — recorded, not fixed.

`GET /v1/usage` (plan 2.7, deferred here on purpose) reports the buckets in an extensible
`meters[]` shape. The usage ledger, which no `/v1` route wrote before, is now written by
`withPartnerAuth` for every response produced once the key is known; a failure before the key
resolved writes nothing, which is the non-enumerability rule, not a gap.

**Transitional state, by design.** The migration replaces `reserve_partner_quota` at apply time,
so the code still deployed at that moment reserves into the new bucket and never confirms. Until
the new code ships, successful sends sit in `usage_reserved`. The total is correct throughout.

## 10.5 — environment-bound keys

Staging will be a **restored production dump** (plan §0.6), so "the hash is not in the table" is
not a control anyone gets to rely on. Two layers, both answering the unknown-key 401:

- the door accepts only its own environment's prefix (`pk_live_` production, `pk_test_` staging)
  before any lookup — a production door never confirms that a staging key exists;
- `partner_api_keys.environment` must equal the door's after the lookup — the layer that holds for
  a restored dump and for a hand-inserted row whose prefix lies.

The door reads `PARTNER_API_ENVIRONMENT`; unset is production (the one deployment there is has it
unset), any other value refuses every key with `internal_error` and a log line naming the
variable. The prefix ↔ environment rule lives in one SQL function both minting paths consult;
rotation inherits the environment and has no parameter that could change it.

**A defect the harness caught.** The first migration created an 11-argument `create_partner_key`
beside the 10-argument one — `CREATE OR REPLACE` with a different parameter list *adds* an
overload — and every existing call became "not unique". The old overload is now dropped in the
same transaction, and the suite asserts exactly one overload exists.

## 10.3 / 10.2 / 10.4 / 10.6 — contract, Postman, documentation

`POST /v1/messages` and `GET /v1/templates` were served but undocumented since Phase 3; the
tracked gap is now empty. Documenting them surfaced three promises the contract made that the code
did not keep, all fixed in code rather than softened in prose: a `/v1` 429 now publishes
`X-RateLimit-Limit`/`Remaining: 0`/`Reset`; every `/v1` replay says `Idempotency-Replayed`; a
2xx send body carries `request_id` (D2). `POST /v1/media` now declares the `Idempotency-Key` it
always required.

The Postman collection is generated from the contract (`scripts/generate-postman.ts`), and CI
fails when the committed JSON is not what the generator produces. Path parameters are Postman
variables with synthetic values; every credential is a `REPLACE_ME` placeholder.

`docs/developer/` is the PRD §32 set. A claim-by-claim review against source found sixteen false
or unverifiable statements in the first draft — a route under the wrong scope, a "5-minute
tolerance" presented as a Postora constant, a response shape that does not exist, reconciliation
by an id the send never returns, an invented deprecation date — all corrected. The lesson is the
one docs-guard exists for: prose that reads as authoritative is not evidence of anything.

## 10.8 — the chain test is not the certification

`supabase/functions/partner-api/e2e/chain.e2e.test.ts` runs the real `/v1` handlers against the
harness database through PostgREST, so the idempotency claim, the quota reservation, the dispatch
intent, the webhook outbox and the reconciliation are the real SQL. Only the provider and the
partner's endpoint are stubbed, at the fetch boundary; the webhook hop recomputes the HMAC over the
exact raw body. Nine scenarios cover the plan's five required failure classes.

`docs/api/certification.md` says, in so many words, that certification has **not** been
performed: it needs the staging environment (0.6) and an external client, and Danat has no WABA.

## Known gaps carried forward

- **Replayed failures on `/v1` are alias-shaped.** A stored 4xx verdict from a failed send is
  replayed verbatim, and the stored body is the alias envelope (`{success:false, error:{…}}`),
  not D2's. Pre-existing; not touched here.
- **`partner_api_usage` is not readable by `service_role`** under the least-privilege grants;
  the E2E fixture grants SELECT in the throwaway database only. Nothing in production reads it,
  so nothing in production is affected — but a future `GET /v1/usage` ledger view will need a
  deliberate grant.
- `src/integrations/supabase/types.ts` does not know the new columns. Regenerate from production
  after the migrations are applied; not hand-edited here.
- `check-edge-env-drift.mjs` reports ten pre-existing undeclared variables, none from this phase.

## Delegation record

Five briefs to OpenCode (`opencode/muse-spark-1.2-contributor-free`), one worktree, sequential,
each reviewed and re-verified here before commit. Every task produced plausible, complete-looking
work; three of five carried a defect the model could not see because it could not run the harness
or verify prose against source (the overload ambiguity, the backfill double-count, the sixteen
documentation claims). The review, the harness, and the mutation checks are not optional steps
around delegation — they are the delegation.
