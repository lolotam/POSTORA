# Postora Security Hardening Audit — 2026-06

**Scope:** entire `supabase/functions/`, `src/`, `infra/`, `scripts/`, `supabase/migrations/`. Read-only audit.
**Target stack:** self-hosted Supabase at `https://api.postora.cloud` (Dokploy VPS). No Supabase Cloud, no `efruibswazzuuupgyzmf` runtime targets.
**Output:** Phase 1 risk register + Phase 2 prioritized roadmap. No code, SQL, or env changes in this pass.

---

## 1. Summary

| Severity | Count |
|----------|-------|
| Critical | 6 |
| High     | 9 |
| Medium   | 8 |
| Low      | 5 |

Most of the OAuth / cron / webhook plumbing is in good shape (`_shared/cron-auth.ts` is used widely, `_shared/auth-helper.ts` does service-role detection with `timingSafeEqual`, Stripe/Resend/WhatsApp/Threads webhooks all verify signatures, OAuth state is HMAC-signed). The concentrated risk is in: (a) a small set of **unauthenticated cron-style endpoints**, (b) **OTP generation using `Math.random()`**, (c) **user-enumeration in the OTP flow**, (d) **wildcard CORS on privileged endpoints**, and (e) **`tiktok-webhook` using a static bearer instead of signature verification**.

| # | file | issue | sev | exploit | fix | SQL | Lov | Srv |

| A1 | `supabase/functions/send-reset-otp/index.ts:25` (`generateOTP`) | OTP uses `Math.random()` — predictable PRNG, not CSPRNG | **Critical** | Attacker who can sample a few OTPs (e.g. own account) can predict the PRNG state and forge another user's reset code within the 10-min window | Replace with `crypto.getRandomValues(new Uint32Array(1))` and mod into the 6-digit range with rejection sampling | no | yes | redeploy fn |
| A2 | `supabase/functions/send-reset-otp/index.ts:118` (`MFA_NOT_ENABLED` branch) | Returns distinguishable 400 if user exists but has no MFA, vs generic 200 if user doesn't exist | High | User enumeration: attacker probes emails and learns which are registered + which lack MFA (then targets weaker accounts) | Always return the generic success response; surface the MFA hint only on the authenticated `/settings` page | no | yes | redeploy fn |
| A3 | `supabase/functions/verify-reset-otp/index.ts` | Increments attempt counter only AFTER lookup matches; an attacker who never matches gets unlimited attempts on the email (no `attempts` row exists until first send) | High | Brute-force pressure on a known target's OTP space across many `send-reset-otp` requests | Add per-email rate limit on `send-reset-otp` (e.g. 3 / hour) using `password_reset_otps.created_at`; also penalize lookup misses | manual SQL: index on `(email, created_at)` if absent | yes | redeploy fn |
| A4 | `src/hooks/useAuth.tsx` + `Auth.tsx` | Confirm `onAuthStateChange` registered before any `getSession`/`getUser` (per project memory) and that `Auth.tsx` doesn't `console.log` access tokens | Medium | Race/leak risk | Spot-fix any `console.log(session)` found; confirm listener ordering | no | yes | n/a |
| A5 | `verify-reset-otp` password rule (`length < 6`) | Weak password policy: 6 chars min | Medium | Brute force | Raise to 10+ with a strength check; align with HIBP toggle | no | yes | redeploy fn |
