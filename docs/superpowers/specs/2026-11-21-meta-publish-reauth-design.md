# Reconnect an account after Meta rejects its publishing grant

**Decision.** Medium, no migration. Astra 6.2 at medium effort designed the change. The owner elected no plan debate and selected OpenCode MiniMax M3.1 Flash Coding Plan for both implementation and tests. Baseline commit `2bc5e95f7a79fdd370e5c733e3579515036a747b`.

## Evidence and expected outcome

Native Facebook Reels and Instagram publishes succeeded earlier and later failed with “Error validating access token: The user has not authorized application ...”. The affected rows were active, with future token expiry and `needs_reauth=false`. Expiry estimates do not establish that the user still authorizes the app. Meta documents this example as an `OAuthException` with code 190 and subcode 458. The incident supplied message text, not a captured structured response. [Meta token debugging](https://developers.facebook.com/docs/facebook-login/guides/%20access-tokens/debugging/) · [Graph API error handling](https://developers.facebook.com/docs/graph-api/guides/error-handling)

At this commit, `postFacebookReel` parses each response and throws only the provider message on start, upload and finish. Both native Instagram login paths also reduce create failures to strings. Their final POST goes through `publishContainer`, which creates an ordinary Error from the message. The shared status poller retains a reason/retry classification, and `checkContainerOnce` maps a non-OK response to waiting. None of those conversions records revoked authorization against the account. The dashboard already queries active, user-owned rows with `needs_reauth=true` every minute in `src/hooks/useAccountsNeedingReconnect.ts`. Persisting the flag makes the existing reconnect flow available on its next successful read.

## Provider observation

Use the narrow documented signature at the parsed provider-response boundary. Reuse `_shared/metaErrors.ts` to decode the actual HTTP status and body. Require type OAuthException, numeric code 190 and numeric subcode 458 together. The shared permanent predicate alone accepts additional subcodes in isolation and a wider range of 190 errors. Leave refresh classification intact. Ignore contradictory explicit transient signals, throttled or timeout responses, transport errors, malformed bodies, rendering diagnostics, content rejection, generic permission errors and messages that merely contain these words or numbers. The existing parser gives definitive structured evidence precedence over an otherwise generic 5xx.

Attach the observer only to essential native operations: the three Facebook Reel phases and both Instagram hosts' container creation, child creation, readiness polls and final media publish, including resumed containers and ambiguous-publish status checks. Classify only the top-level Graph error envelope. Keep the publish attempt's account snapshot in memory. Use the account freshly loaded for a resumed invocation. Never serialize that snapshot in checkpoints. No observation on permalink, comment, place, metadata enrichment or other best-effort calls.

Observe the parsed result before legacy adapters flatten it or recovery catches it. Keep the same reply and control flow for result settlement, independent stories, mixed success, deferral and duplicate suppression. An unanswered final POST can already be live. Bound its follow-up status request through body parsing, and preserve the uncertain outcome and its checkpoint even when the GET reports a revoked grant. Start the bounded account write alongside publishing and await started writes in request cleanup after every destination has been processed. A reply read after its deadline cannot prevent a later timely observation. Preserve actionable error messages after redacting the request credential, authorization headers and URLs. Keep raw Graph bodies out of diagnostics.

## Conditional account write

The initial account query uses `select("*")`, owner, platforms and active status. The native functions use the selected account's access token. Capture the unmodified database `updated_at` alongside that token when binding the observer. The baseline schema installs `update_social_accounts_updated_at` before **every** row update. Both Facebook and Instagram OAuth reconnect writers explicitly clear reauth and set updated_at. Refresh success updates the stored credential and clears reauth. Thus a concurrent refresh, same-token reconnect or unrelated account update ordinarily changes the observed row version. The timestamp is a conservative row-wide fence, not a unique credential counter. Losing an observation after unrelated writes is acceptable. A transaction timestamp can repeat across writes within a transaction.

Keep credentials out of PostgREST filter URLs. Prefer the original database row version as the server-side credential snapshot fence, with a local equality check that the failed request used the selected token. Skip if either value is absent, substituted or reconstructed. Never read a new timestamp after failure to re-arm a stale observation. Use one conditional UPDATE on account id, trusted post owner, observed platform, active status, exact original timestamp and needs_reauth false or null. Change only `needs_reauth=true` and `last_refresh_error` to a stable message such as “Meta authorization was revoked. Reconnect this account.” Let the database update its timestamp. Zero matches is a successful no-op. On a storage failure emit one sanitized warning without changing publish settlement. Never change credentials, expiry, refresh counters or active status.

The refresh failure RPC `partner_record_refresh_failure` has an account-id interface, refresh counters and partner notification semantics. It cannot express these write predicates. This publish update drives dashboard visibility only. It does not promise refresh-event fan-out. Existing successful reconnect writers retain authority to clear the flag.

## Scope and acceptance

Immediate n8n publishing invokes process-post after post creation. Scheduled publishing invokes it after its own preflight. A scheduler refusal before dispatch has no observed publish response. Neither caller needs new logic. No change to API responses, UI, grants, migrations, generic retries, other platforms, Facebook non-Reel formats or independent job runners. No customer-specific backfill, resend or production publish test.

Acceptance requires mocked positive cases on each native route, stale and cross-tenant no-op cases, unrelated failures, idempotent updates, preserved partial/deferred outcomes and credential-free diagnostics. Delivery ends with exact-head review and CI, then evidence that the automatic runner served the merged code and the function booted.
