## Delivered behavior

The `drain` action claims one real platform-owned job through a service-only coordinator. A private two-row platform-turn table advances atomically with each native claim, so successive `all` invocations give the other platform a turn even when the first platform repeatedly finishes only partial work. Native claims retain their parent-first account/authority locks. No generic replacement job queue was introduced.

The claimed-generation state reader returns the checkpoint and operations in one fenced RPC. Inventory reserves a database UUID against the expected prior cursor/page count before HTTP. Its response commits that exact reservation once; identical replay returns the same receipt, conflicting content refuses, and reclaim replaces the old request UUID. Page IDs/cursor advancement commit together. Foreign Page IDs, absent/repeated next cursors, more than 500 accumulated IDs and the 100-page bound cannot become complete inventory. Exactly 500 IDs with actual provider exhaustion may complete; 500 IDs with more pages remain truncated.

The worker plans the last closed provider-calendar day and its correction day, with real America/Los_Angeles DST boundaries. It reserves metric captures before HTTP, skips accepted operations after restart and rotates previously attempted failures behind unvisited operations. Post metadata is fetched through each real provider adapter after restart instead of adding an unbounded payload store. Metadata and cell values enter the existing SQL writer atomically. Missing/malformed/version-mismatched values retain their unavailable causes; a provider-reported zero remains zero.

One invocation retains the shared 40-second deadline, five-second dependency bounds and final audit reserve. Each visit permits at most two inventory pages, eight capture operations and 20 physical provider calls. The whole invocation shares 50 visited jobs. A known visit budget stop releases partial work; an unknown read/write outcome stops the complete invocation and leaves the claim for durable reconciliation. Provider requests repeat current job authority immediately before HTTP. No new worker refreshes tokens or manufactures grants.

The Meta usage parser was moved from the existing Instagram transport into `_shared/metaUsage.ts`; the existing owner transport imports it under its original public name, while the new collection uses the same parser. C3 persists only bucket-scoped usage/backoff through `record_instagram_provider_throttle_http` with all three Instagram job arguments explicitly null. Keys bind platform/app/current credential authority without storing credentials. Every later request reads the persisted bucket first. Rate limits park the appropriate Facebook/Threads job through its own completion RPC; a new due date cannot reset the shared backoff. Usage-store failures propagate outside the provider error catch.

The `retention` action derives owners server-side and uses the independent retention policy. It pins one UTC 365-day floor, shares 50 targets/500 actual physical children across both platforms, distinguishes `deleted` from `wouldDelete`, and records the floor in its final audit. Real no-op cleanup advances only private visit ordering; report revisions remain unchanged. Dry runs do not advance visits or revisions. Exhausting the child budget remains partial, including on the last visited target. Existing native cleanup keeps its live-lease and ownership fences.

The schedule migration reconciles exactly six names, all inactive: each of `facebook-analytics` and `threads-analytics` has `-enqueue-daily` at `5 * * * *`, `-drain` at `*/5 * * * *`, and `-retention` at `35 * * * *`. Commands use the registered route, exact strict bodies, runtime `get_cron_secret()` and a 60-second outer HTTP bound. Missing pg_cron, pg_net or the secret reader refuses before any mutation. Reapplication pauses previously active instances and preserves unrelated jobs/settings.
