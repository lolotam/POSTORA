# Findings: Postora n8n Trigger receives no message events (investigator: opencode)

Working tree: branch `fix/ig-webhook-igid-lookup` @ `51e72d3e`. `origin/main` @ `27cf14a3`.
Version facts pinned first, because two of them reframe the whole investigation:

- npm `n8n-nodes-postora`: **1.1.14** (2026-07-17) introduced PostoraTrigger with `checkExists() { return Boolean(staticData.webhookId) }` (`git show 5c94c207:Postora-n8n-community-node/dist/nodes/PostoraTrigger/PostoraTrigger.node.js:49-51`). **1.2.0** (2026-08-20) and **1.2.1** (2026-08-21) replaced it with a server-verifying `checkExists` (`Postora-n8n-community-node/nodes/PostoraTrigger/PostoraTrigger.node.ts:99-143`). Any n8n instance that installed the trigger before 2026-08-20 runs the old behavior unless upgraded.
- The entire server-side message→n8n fan-out did not exist before commit `6092253c` (2026-08-20, in `origin/main`): `n8nMessagingDispatch.ts`, the dispatch calls in the webhooks, and `message.*` in `ALLOWED_WEBHOOK_EVENTS` are all new (`supabase/functions/_shared/n8nMessagingDispatch.ts:1-225`; `supabase/functions/n8n-api/index.ts:24-27`). Edge functions deploy **manually** (AGENTS.md step 7), so the running container may predate this.
- The Instagram id-routing fix `8d237c2a` (2026-08-21) is **NOT in origin/main** — it lives only on this branch (`git merge-base --is-ancestor 8d237c2a origin/main` → false).

## 1. Ranked candidate root causes

### #1 (Instagram — near-certain, proven code gap in origin/main): IGID routing miss — the webhook's `entry.id` can never match any stored column

For accounts connected via **direct Instagram Login** (`instagram-oauth`, `source: instagram_business_login`), connect stores the **app-scoped id** in *both* columns that `findAccountForRecipient` on `origin/main` searches, and stores the **Instagram-scoped id (IGID)** — the id Meta's messaging webhooks actually address the account by — only in `account_metadata.ig_igid`, which main never reads:

- `supabase/functions/instagram-oauth/index.ts:168-172` — `igUserId = String(profileData.id)` (app-scoped); `igScopedId = profileData.user_id` (IGID), with the comment "Messaging webhooks address the account by its IGID".
- `supabase/functions/instagram-oauth/index.ts:200-210` — `platform_user_id: igUserId` (app-scoped) and `account_metadata.ig_user_id: igUserId` (app-scoped again); only `account_metadata.ig_igid: igScopedId` (:210) holds the webhook-facing id.
- `origin/main` snapshot of `supabase/functions/facebook-instagram-webhook/index.ts:27-46` — lookup matches only `platform_user_id` (= app-scoped id) then `account_metadata->>ig_user_id` (= the same app-scoped id). **No `ig_igid` probe.**

Result at runtime (main code): verified DM arrives → `findAccountForRecipient` returns `null` → `continue` with a single `console.warn` → no inbox row, no dispatch, HTTP 200 to Meta, workflow never fires. That matches the previously recorded symptom "no inbox rows and no warning" exactly. The fix already exists in the working tree (`supabase/functions/facebook-instagram-webhook/index.ts:41-50` loops `["ig_igid","ig_user_id"]`) but is unmerged and — per the manual deploy model — almost certainly not live unless someone deployed this branch.

**CONFIRM:** send a test DM, then grep the `facebook-instagram-webhook` container logs for `No matching instagram account found for recipient <X>` (warn emitted at `supabase/functions/facebook-instagram-webhook/index.ts:152`). If present, compare `<X>` (the IGID) to storage: `SELECT id, platform_user_id, account_metadata->>'ig_igid' AS igid, account_metadata->>'ig_user_id' AS iguid FROM social_accounts WHERE platform='instagram' AND is_active;` — if `<X>` equals `igid` but neither `platform_user_id` nor `iguid`, cause proven. **REFUTE:** absence of both that warn and `[fb-ig-webhook] Received verified instagram event` in logs (Meta never delivered → see #5).

### #2 (all platforms, if n8n runs node ≤ 1.1.15): stale/mis-scoped registration never refreshed by the old `checkExists`

npm 1.1.14–1.1.15 `checkExists` is `Boolean(staticData.webhookId)` (`git show 5c94c207:.../dist/nodes/PostoraTrigger/PostoraTrigger.node.js:49-51`). Consequences while an old node version stays installed:

- The server-side row's `events` are frozen at whatever the **first** activation sent. Editing Events to `["message.received","message.instagram"]` and reactivating calls `checkExists` → `true` → `create()` never runs → the row can still hold the default `["post.completed"]`. Dispatch then filters it out in `matchesSubscription` (`supabase/functions/_shared/n8nMessagingDispatch.ts:147-153`) — silent drop. This is precisely the failure class the 1.2.0 rewrite documents (`Postora-n8n-community-node/nodes/PostoraTrigger/PostoraTrigger.node.ts:95-99`).
- Same trap for a deleted/deactivated row (`is_active:false` after 10 failures, `n8nMessagingDispatch.ts:213`, or a stale/changed callback URL): `staticData.webhookId` survives, activation "succeeds", nothing re-registers.
- Test-vs-production callback URL: an early "Listen for test event" registers the `webhook-test/...` URL; later production activation never re-registers under the old node.

**CONFIRM (single curl answers it):** `curl -H "x-api-key: <danat-future key>" https://api.postora.cloud/functions/v1/n8n-api/api/v1/webhooks` — inspect `webhook_url` (must be the production `…/webhook/<n8n-webhookId>` URL), `events` (must include `message.received` or `message.instagram`), `is_active` (must be true) (`supabase/functions/n8n-api/index.ts:1517-1546`). Also check the installed package version in n8n (Settings → Community nodes → `n8n-nodes-postora`). **REFUTE:** listing shows an active row with the correct URL and both events, and node ≥ 1.2.0.

### #3 (all platforms): tenancy split — API-key user ≠ social-account owner

Registration is keyed by the API key's `profiles.id`: `authenticateApiKey` (`supabase/functions/n8n-api/index.ts:75-99`) → key `n8n_webhook_${userId}_${webhookId}` (`n8n-api/index.ts:1471-1472`). Dispatch loads destinations with `like('key', 'n8n_webhook_' + userId + '_%')` where `userId` is **`account.user_id`** — the owner of the account that received the message (`supabase/functions/facebook-instagram-webhook/index.ts:183-186`; `n8nMessagingDispatch.ts:110-113`). If the "danat-future" credential's API key resolves to a different `profiles.id` than the owner of the IG/WhatsApp `social_accounts` row, the two never intersect and the drop is silent (empty destination list, no log line at all).

Multi-tenant surfaces that make this reachable: workspaces/partner model — `social_accounts.workspace_id` + `workspaces.owner_id` (`supabase/functions/partner-api/index.ts:122-127,169-171`; `supabase/functions/whatsapp-webhook/index.ts:165-188` resolves legacy accounts through the owner's personal workspace). A WhatsApp account connected inside a partner workspace is owned by that workspace's `user_id`, which may differ from the user holding the n8n API key. There is no workspace indirection in `n8n-api` — it is strictly `profiles.api_key → userId`.

**CONFIRM (SQL):** `SELECT p.id AS api_key_user FROM profiles p WHERE p.api_key = '<danat-future key>'; SELECT id, user_id, workspace_id, platform FROM social_accounts WHERE platform IN ('instagram','whatsapp') AND is_active;` — if `user_id` ≠ `api_key_user` for the tested account, cause proven. Cross-check with `SELECT key, value->>'is_active', value->'events' FROM app_settings WHERE key LIKE 'n8n_webhook_%';`.

### #4 (all platforms, deployment state): edge functions container predates `6092253c`

Before 2026-08-20 there was **no** `dispatchMessageEvent`, no dispatch calls in any webhook, and no `message.*` in `ALLOWED_WEBHOOK_EVENTS` (`git show 6092253c --stat`; `n8n-api/index.ts:24-27`). Edge functions are redeployed manually via SSH (`AGENTS.md` → Task Execution Workflow step 7). If the Contabo `functions` container was last deployed before 2026-08-20 (or before `8d237c2a` for the IGID fix), **no** DM dispatches for any platform, regardless of registration.

**CONFIRM:** on the server (ssh-contabo-mcp): `docker exec <functions-container> grep -c "n8n-dispatch" /home/deno/functions/facebook-instagram-webhook/index.ts` (or compare the file's SHA256 against the repo per `docs/runbooks/deploy-edge-function.md`); simpler: grep container logs for `[n8n-dispatch]` or `[background]` lines (`supabase/functions/_shared/background.ts:28`) — their absence on any message proves old code. **REFUTE:** logs show `[fb-ig-webhook] Received inbound instagram message` (emitted at `facebook-instagram-webhook/index.ts:206`) for the test DM.

### #5 (Instagram, Meta-side): app/ account webhook subscription never established

- Direct-login IG: `subscribeDirectAccountToWebhooks` POSTs `{ig-id}/subscribed_apps?subscribed_fields=messages` but is **best-effort — a failure is only a `console.warn` and connect still "succeeds"** (`supabase/functions/instagram-oauth/index.ts:46-58`, called at `:239`).
- IG-via-Facebook-Page flow subscribes only the **page** with `subscribed_fields=messages,messaging_postbacks` (`supabase/functions/facebook-oauth/index.ts:188-195`, called at `:754,:938`); the standalone IG store path (`store_instagram`, `facebook-oauth/index.ts:1011-1071`) performs **no** subscription at all.
- The app-level Webhooks product configuration (callback URL + `messages` field under the Instagram product in the Meta App Dashboard) is verified by the GET challenge handler (`facebook-instagram-webhook/index.ts:96-108`) but nothing in code can create it — it is a manual dashboard state.

If the subscription is missing, Meta never POSTs, so nothing downstream can fire.

**CONFIRM:** function logs for the test window — absence of `[fb-ig-webhook] Received verified instagram event` (`facebook-instagram-webhook/index.ts:133`) proves Meta never delivered; then check the Meta App Dashboard → Webhooks → Instagram → `messages` field subscribed + the account-level subscription. The envelope log at `:239-248` distinguishes "delivered but produced no message" from "never delivered".

### #6 (IG/FB only): idempotency drop on duplicate `external_event_id`

`recordInboxEvent` upserts with `onConflict: "social_account_id,external_event_id", ignoreDuplicates: true` and returns `"duplicate"` when no row came back; dispatch runs **only** on `"inserted"` (`supabase/functions/facebook-instagram-webhook/index.ts:166-204,268-291`, constraint `UNIQUE(social_account_id, external_event_id)` in `supabase/migrations/20260716123000_live_messaging_events.sql:10`). `social_inbox_events` has no other writer in the codebase (grep across `supabase/functions` + `src` — only readers), so a *first* DM can never be pre-claimed by history sync/backfill. But a Meta retry after a dispatch that failed in-flight *is* permanently suppressed ("duplicate" → skip). Not a first-message failure mode; ranked low. **CONFIRM:** `SELECT * FROM social_inbox_events WHERE external_event_id = '<mid from Meta>'` — row exists with no n8n execution ⇒ dispatch was skipped or failed after insert. **Note:** WhatsApp dispatch is *not* gated on this table (own `whatsapp_messages` dedupe, `whatsapp-webhook/index.ts:380-425`), so this cause cannot explain WhatsApp.

### #7 (delivery layer, silent): `deliverToDestination` swallows errors; 10 failures permanently deactivate the row

`deliverToDestination` catches every error into `console.error` + failure counter (`n8nMessagingDispatch.ts:186-194`); `updateDestination` sets `is_active:false` at `failure_count ≥ 10` (`:212-218`) and `loadDestinations` filters inactive rows (`:137-140`). A stale callback URL (changed n8n tunnel/domain), an n8n host unreachable from the Contabo VPS, or a per-hop SSRF rejection at delivery time (`webhookSecurity.ts:107-109`) all produce the same invisible death spiral. **User-visible signal: none inside n8n.** The only surface is `GET /api/v1/webhooks` returning `is_active` (`n8n-api/index.ts:1534-1540`) — which node ≥ 1.2.0's `checkExists` also uses to self-heal on reactivation (`PostoraTrigger.node.ts:121-128`). **CONFIRM:** the same curl as #2 — `value.failure_count` / `is_active:false` (via SQL: `SELECT key, value->>'failure_count', value->>'is_active' FROM app_settings WHERE key LIKE 'n8n_webhook_%';`) plus `[n8n-dispatch] ... failed:` log lines.

## 2. Answers to the seven numbered questions

1. **TENANCY.** `n8n-api` maps API key → `userId` via `profiles.api_key` exact match (`n8n-api/index.ts:75-99`); the registration key embeds that user (`:1471-1472`). Dispatch uses `account.user_id` returned by `findAccountForRecipient` (`facebook-instagram-webhook/index.ts:150,183-186`; IG lookup `:25-52`; WhatsApp `whatsapp-webhook/index.ts:165-188`). Yes — a credential whose API key belongs to a different Postora user than the account owner makes registration and dispatch disjoint; the drop is totally silent (empty destination array). Partner/workspace indirection exists (`partner-api/index.ts:122-127` resolves accounts by `workspace_id` with `ownerId: account.user_id`; workspaces have `owner_id`), but `n8n-api` itself has **no** workspace layer — tenancy is raw `profiles.id` equality. See cause #3 + SQL.
2. **IDEMPOTENCY DROP.** Duplicates return `"duplicate"`, and only `"inserted"` dispatches (`facebook-instagram-webhook/index.ts:277-290` gating at `:179-204`). No other code writes `social_inbox_events` (only readers in `src/hooks/useMessaging.ts:152,178`), so history sync/AI backfill cannot pre-claim ids. The reachable suppression is: insert succeeds → dispatch fails (delivery error, deadline skip `n8nMessagingDispatch.ts:96-99,104-107`) → Meta retries the same `mid` → `"duplicate"` → never dispatched. Cause #6.
3. **SSRF GUARD.** `validateWebhookTarget` requires HTTPS + public hostname, rejecting internal names, and IPv4/IPv6 loopback/private/link-local/reserved ranges (`webhookSecurity.ts:3-93`); `postWebhook` re-validates every redirect hop at delivery (`:100-136`). At registration the 400 is **surfaced**: `create()` awaits `httpRequestWithAuthentication` and throws, so n8n activation fails visibly (`PostoraTrigger.node.ts:144-163`) — *unless* the old node's `checkExists` short-circuits (`true`) and `create()` never runs, which is how an invalid/unregistered state can coexist with an "active" workflow (cause #2). Non-standard ports and public DNS names are accepted; an unresolvable host fails later at delivery, silently (cause #7).
4. **STALE REGISTRATION.** Reachable and real — but **version-dependent**: with npm ≤ 1.1.15 (`5c94c207` dist `:49-51`), re-activation can never re-register: `checkExists` is `Boolean(staticData.webhookId)`, so a deleted/deactivated/mis-scoped `app_settings` row is invisible forever; only deleting static data or the workflow fixes it. With npm ≥ 1.2.0 the question is answered by `PostoraTrigger.node.ts:99-143`: `checkExists` now GETs `/api/v1/webhooks`, matches id + `is_active !== false` + exact callback URL + exact event set, unregisters the stale row and returns `false` → `create()` re-registers (correct fix, already shipped). The user's workflow was built during the 1.1.14–1.1.15 window (trigger existed, message-dispatch did not), so an old installed version is likely.
5. **EVENT NAME MISMATCH.** Platform is `body.object === "instagram" ? "instagram" : "facebook"` (`facebook-instagram-webhook/index.ts:132`), and the dispatched event is `message.<platform>` (`n8nMessagingDispatch.ts:143-145`). For this user's subscription (`message.received` **and** `message.instagram`), `matchesSubscription` matches on `message.received` regardless of the computed platform (`n8nMessagingDispatch.ts:152`), so a page/instagram object mixup cannot drop the event — **refuted for this configuration**. It only bites if the stored registration events are stale (cause #2) or lack `message.received`.
6. **META SUBSCRIPTION.** For an IG DM to reach `facebook-instagram-webhook`, the app must be subscribed at the app-dashboard level to the Instagram `messages` webhook field, and the account must be subscribed: direct-login accounts via `{ig-id}/subscribed_apps?subscribed_fields=messages` (`instagram-oauth/index.ts:46-58`, best-effort, warn-only on failure, called at `:239`); page-linked flows via the **page's** `subscribed_apps` with `messages` (`facebook-oauth/index.ts:188-195`, called at `:754,:938`); the `store_instagram` standalone path performs **no** subscription (`facebook-oauth/index.ts:1011-1071`). So yes — the code is responsible at connect time and it can silently fail or never be called. See cause #5 and the log-based discrimination.
7. **DELIVERY FAILURE.** `deliverToDestination` swallows everything into `console.error` + `failure_count` (`n8nMessagingDispatch.ts:186-194`), and `updateDestination` deactivates at 10 (`:212-218`). The only user-visible signal that exists anywhere is `GET /api/v1/webhooks` exposing `is_active` (`n8n-api/index.ts:1534-1540`) — nothing appears inside n8n; deactivated rows stop matching in `loadDestinations` (`:137-140`) with zero telemetry to the subscriber. Node ≥ 1.2.0 converts that signal into self-healing on reactivation (`PostoraTrigger.node.ts:121-128`). Otherwise: none. Cause #7.

## 3. Single best hypothesis

**"The direct-login Instagram account's webhook-facing id (IGID) is stored only in `account_metadata.ig_igid`, which `origin/main`'s `findAccountForRecipient` never queries — so every inbound Instagram DM fails account resolution and is dropped (warn-only) before any inbox insert or n8n dispatch; the fix (`8d237c2a`) exists on `fix/ig-webhook-igid-lookup` but is neither merged to main nor provably deployed, and any WhatsApp/other-platform silence is a second, co-occurring state: an n8n instance still running node ≤ 1.1.15 whose frozen registration (stale `events`/URL or inactive row) is never re-created by the old `checkExists` — or an edge-functions container not yet redeployed with the 2026-08-20 dispatch code."**

The IG half is proven from source (there is no code path on main by which a direct-login IG DM can find its account row). The cross-platform half must be settled by the three CONFIRM steps (webhook listing curl, function logs, node version).

## 4. Recommended fixes (description only — DO NOT APPLY)

1. **Merge + deploy `fix/ig-webhook-igid-lookup` (`8d237c2a`)** — `supabase/functions/facebook-instagram-webhook/index.ts`, `findAccountForRecipient`: already correct in the branch (probes `account_metadata->>ig_igid` then `ig_user_id`, `:41-50`). Land it to `main`, then redeploy the function per `docs/runbooks/deploy-edge-function.md` (copy + SHA256 verify + `docker compose up -d --no-deps functions`). This is the mandatory fix for cause #1.
2. **Backfill `ig_igid` for existing rows / make connect canonical** — `supabase/functions/instagram-oauth/index.ts`: it already stores both ids (`:200-210`); optional one-off SQL backfill is unnecessary since connect always wrote `ig_igid` from 6092253c-era code — but if any rows predate it, re-connect or an admin script must populate `ig_igid`. Verify with the SQL in cause #1.
3. **Force re-registration for affected users** — after upgrading the n8n community node to ≥ 1.2.1 (npm `1.2.1` published 2026-08-21), deactivate + reactivate the workflow; the new `checkExists` unregisters the stale row and re-registers with the current events + production callback URL (`PostoraTrigger.node.ts:99-143`). No server change needed for this part.
4. **`supabase/functions/_shared/n8nMessagingDispatch.ts`, `deliverToDestination`/`updateDestination`**: surface delivery health — include `last_failure_at`/`last_error` in the `app_settings` value alongside `failure_count` and expose them in `GET /api/v1/webhooks`; optionally emit a `[n8n-dispatch] destination deactivated` `console.error` when crossing `failure_count >= 10` so log alerts catch the death spiral. Also consider resetting `failure_count` to 0 on re-registration (a fresh `handleRegisterWebhook` write starts at 0 implicitly — but a `create()` after `checkExists` mismatch leaves the *old* row active until unregistered; the node already handles the retire).
5. **`supabase/functions/instagram-oauth/index.ts:46-58`**: stop swallowing `subscribeDirectAccountToWebhooks` failures — persist a `webhook_subscription_ok` flag (or an error message) into `account_metadata` so the UI/connection-health page can show "DM webhooks not active", and retry once. Same for `facebook-oauth/index.ts:188-195`.
6. **`supabase/functions/facebook-oauth/index.ts:1011-1071` (`store_instagram`)**: call the IG-level subscription (or reuse `subscribeDirectAccountToWebhooks`) after `mergeUpsertInstagram`, so standalone IG accounts actually receive messaging webhooks.
7. **Optional hardening (not this incident):** in `facebook-instagram-webhook`, when `findAccountForRecipient` misses, persist the envelope (like the `handledMessages === 0` log at `:239-248`) so "delivered but unroutable" is queryable, not just a log line.
