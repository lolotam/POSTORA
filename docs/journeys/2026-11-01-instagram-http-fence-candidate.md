# Instagram stale-claim HTTP boundary — local candidate

Date: 2026-11-01. Scope: owner collection readiness under the [Meta analytics plan](../plans/2026-11-01-meta-analytics-completion.md), A6. No production version, logs or account data were inspected for this investigation; no production migration, deployment or switch change occurred.

## Proven failure

The new real Auth/PostgREST/worker journey changes the target's credential generation while the synthetic Meta response is in flight. Existing SQL fences correctly refuse the old claim with SQLSTATE `40001`. Native SQL tests return that error promptly, but the same operation through local PostgREST 12.2.11 does not return it: Hasql repeatedly retries the deterministic refusal. The worker eventually abandons the visit as `storage_error`, stops the run, and the database request can continue after its HTTP caller has timed out.

Evidence included a direct PostgREST stale-write probe timing out, rapid transaction churn and deadlocks in the disposable service, and no changed history rows. The corresponding configured source path is [PostgREST 12.2.11 Query.hs](https://github.com/PostgREST/postgrest/blob/v12.2.11/src/PostgREST/Query.hs#L81), which selects `SQL.transaction`; its declared `hasql-transaction` dependency range is `>=1.0.1 && <1.1`. The [1.0.1.4 retrying-session implementation](https://github.com/nikita-volkov/hasql-transaction/blob/1.0.1.4/library/Hasql/Transaction/Private/Sessions.hs#L13) retries `40001`. That source explains the observed behavior; it is not a claim that the local image's exact compiled Hasql patch was independently identified.

Failed attempts were reported, not counted as successful acceptance. Two earlier fixture requests were corrected to use the actual wire contract (`action: "enqueue"` and `reason_code`). The mutation during the provider response now uses real PostgREST rather than Docker CLI process spawning, keeping fixture work inside the provider deadline. After those corrections, the deterministic `40001` retry still reproduced. The database and HTTP adapter correction, rather than a timeout increase or relaxed assertion, made the journey pass.

## Correction and deployment order

The additive migration `20261101023000_instagram_collection_http_fences.sql` creates five typed, service-only `SECURITY INVOKER` HTTP wrappers. Each delegates to the unchanged canonical function and catches only `40001` with one of the named collection refusal prefixes. It returns a sanitized `PT409` conflict for those refusals. Other errors, including genuine PostgreSQL serialization failures, rethrow unchanged. Native SQL functions and their existing grants/error contracts are unchanged.

The owner's service RPC transport maps snapshot, progress, completion, throttle and direct-credential calls to those wrappers. User RPC names are unchanged. The worker store recognizes the HTTP conflict as the same definitive per-job stale/changed refusal: the refused result never advances success, checkpoint or retry state; previously recorded planning state remains. Other jobs are not stopped by that refusal. No legacy HTTP fallback is added when the wrappers are missing.

The migration is deliberately a separate predecessor to the runtime change. It must be reviewed, approved, merged, applied and verified with schema-cache refresh before the dependent runtime is merged/deployed. The automatic Edge reconciler does not apply migrations. Both steps retain the [owning release approvals](../specs/2026-10-30-instagram-release-gates.md); this candidate grants none of them.
