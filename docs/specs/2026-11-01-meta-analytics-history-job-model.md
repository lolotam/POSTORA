# ADR: durable history for owned Facebook Pages and Threads

**Status:** implementation decision reviewed against source; author corrections recorded in §9. Migration implementation remains subject to normal review, and merge/application each require separate owner approval. No credential repair, collection, retention, pilot or schedule is authorized by this record.
**Date:** 2026-11-01.
**Scope:** C1 of the [completion plan](../plans/2026-11-01-meta-analytics-completion.md), implementing [design §§8–12](2026-11-01-meta-analytics-completion-design.md#8-workstream-4--history-for-facebook-and-threads). The design owns metric meanings, retention eligibility, pilot acceptance and approvals; this ADR owns their concrete storage and concurrency implementation. All names below are proposed unless explicitly identified as existing.

## 1. Decision and source evidence

Choose design §8.2 **option (b): per-platform durable job tables**, reusing the existing runtime-neutral contract and transport. Keep the deployed Instagram owner/competitor queue and credential protocol unchanged.

The existing [durable-job migration](../../supabase/migrations/20261026150000_instagram_durable_collection_jobs.sql) defines owner/competitor targets, a Kuwait capture day, viewer context and Instagram capability generations. Its [worker store](../../supabase/functions/instagram-insights-sync/workerStore.ts) selects Instagram accounts and distinguishes direct Instagram credentials from protected Facebook **User** credentials. Its [receipt decoder](../../supabase/functions/instagram-insights-sync/receipts.ts) closes those exact SQL projections. Facebook Page and Threads readers instead use their platform's operational account token. Reusing that queue or decoder would make platform policy conditional throughout an already deployed security protocol.

| Approach | Consequence | Decision |
|---|---|---|
| Widen the Instagram queue additively | Changes live owner/competitor claims, login contexts and receipt schemas together; couples rollout and rollback | Reject for this task |
| Per-platform owner queues with shared neutral modules | Adds explicit SQL families; platform ownership, credential fences and rollout remain local | Select |
| One new generic replacement queue | Creates a second queue framework and requires an unrelated Instagram migration | Reject |

Share `analyticsCalendar.ts`, `analyticsContract.ts`, `analyticsRegistry.ts`, `analyticsSchema.ts` and `metaAnalyticsTransport.ts` from `supabase/functions/_shared/`. Reuse projection functions only where their semantics fit: `liveAnalyticsMetric` is not a persisted-data assembler. Instagram worker deadline mechanics are currently embedded in its worker; extract them only with both real production callers wired in that change. Do not copy the Instagram SQL, import its complete worker, create unused generic ports, or maintain a second metric registry.

## 2. Ownership, authority and lock order

Every platform table includes `user_id`, `social_account_id` and a checked constant `platform`. Its composite foreign key references the existing `social_accounts(id,user_id,platform)` key. Child-to-job/capture/measurement foreign keys also include owner, account and platform; a valid job UUID alone never grants cross-account attachment. RLS is enabled with no browser policies; revoke raw table and internal-helper access from `PUBLIC`, `anon` and `authenticated`. Also revoke direct mutation privileges on the new tables from `service_role`; service writes use narrowly granted SECURITY DEFINER RPCs that own the lock protocol. Expose only authenticated owner projections and those service RPCs. Definer entrypoints use a fixed search path and derive their target from the verified account/job, not independently supplied payload owner fields.

### Credential authority

- **Facebook:** reuse the existing `facebook_user_credential_connection_fences` high-water, binding connection version and bound User-credential revision/identity, where applicable. The [binding migration](../../supabase/migrations/20261026140000_facebook_user_credential_bindings.sql) makes that high-water survive unbind/rebind. The [refresh lifecycle](../../supabase/migrations/20261027120000_meta_account_refresh_lifecycle.sql) already checks captured account identity, binding presence/version, fence version and health. Collection adopts those authority comparisons, not refresh attempts or refresh RPCs. A Page operational token remains a Page token; never substitute the protected Facebook User token used by Instagram. Admission requires a present, valid connection fence and verified Page/permission binding. Legacy/unbound rows are not assigned an invented generation: refuse collection until their separately approved credential lifecycle establishes that authority. Existing legacy paths outside admission retain their behavior.
- **Threads:** add `threads_analytics_connection_fences`, one row per owned Threads account, with a positive service-controlled `credential_generation`. A database trigger on changes to `access_token`, `refresh_token`, `token_expires_at`, provider identity, ownership/platform, active state or `needs_reauth` advances it atomically under the parent account lock. Add `threads_analytics_permission_observations`, one current service-only row per account, containing `granted_scopes`, `observed_at`, verified provider identity, `state` (`verified` or `unavailable`) and an allow-listed evidence reference. Its RPC accepts only the current captured credential authority and the provider adapter's validated grant observation; a stale observation refuses. A change in trusted scope authority advances the same generation under that lock. Ordinary profile/caption metadata is not permission authority. Initial generation allocation and trusted scope observations are service-only; callers cannot choose or reset the counter. Unbind/rebind on the same account cannot recycle it. Parent deletion removes it. No token, token fingerprint or refresh secret is copied into job provenance.

**Facebook direct-write enforcement:** current connection counters advance through explicit credential RPCs, not all `social_accounts` writes. Add a monotonic `credential_guarded` boolean to `fb_analytics_report_state`, initially false and set true only by separately approved admission. Install a SECURITY INVOKER account trigger which, for a guarded Page, refuses direct security-field updates by `authenticated` and `service_role`. It permits those changes only when the effective database role is the installed owner of the reviewed SECURITY DEFINER credential writers; verify/pin that owner in the schema manifest. Never trust a caller-settable GUC, request JWT role string or body flag to bypass the trigger. Guard token/expiry/refresh, provider identity, owner/platform, active/reauth state and permission authority; ordinary metadata remains writable. Before admitting any Page, route **all** its permitted OAuth/refresh/health/reconnect mutations through the existing fenced writers and review other definer write entrypoints owned by that role for equivalent scope enforcement. A direct service update, including a legacy refresh lane, must refuse rather than silently mutate an admitted Page. Removing collection eligibility never clears this guard or downgrades protected authority. Account deletion remains the existing parent-first lifecycle. C2/C3 prove raw service/owner updates fail, legitimate fenced RPCs succeed, rolled-back changes preserve counters, and reconnect/unbind cannot recycle authority. No second Facebook credential counter or token vault is introduced.

Implementation clarification: that invoker trigger cannot read browser-private report state directly. Use a narrowly scoped SECURITY DEFINER boolean reader for an authenticated account owner, with a generic refusal for foreign ownership and false only for an owned account without report state. Service-role SELECT may remain available; direct mutation is still revoked. Keep the mutation-role decision in the invoker trigger, where `current_user` is the effective caller, rather than accepting a role argument or evaluating it inside the definer reader.

The existing Facebook binding's evidence check requires `verified_facebook_page_id` to be null for a Facebook row; it stores the verified **User** identity. Do not require a nonexistent Page-proof field or treat arbitrary metadata as granted scopes. Add `fb_analytics_permission_observations`, a service-only current provider-observed Page/permission record bound to the actual Page account identity, existing connection high-water and bound credential revision. Its fenced writer advances the existing connection version when trusted permission authority changes; it introduces no second Facebook epoch. The provider adapter verifies the operational Page identity and grant observation, and stale observations refuse. This relation supplies the admission proof required above, independently of the Instagram User-token path.

Changing platform/ownership after history exists is refused by the composite foreign keys; delete/recreate follows the existing account lifecycle. Correctly persisted captures remain historical facts after a later reconnect. Only pending work is invalidated by changed credential authority.

All claim, result-write, force, credential-read and cleanup transactions use this order:

1. Lock parent `social_accounts` rows by ascending ID. One collection/cleanup transaction handles one target. Claims use `NOWAIT` and skip a busy parent; result writes use a bounded lock timeout.
2. Acquire the existing `social_account_guard` advisory. Facebook also observes the existing `instagram_capability` advisory prefix required by its shared credential lifecycle; no new code reverses that order.
3. Collection resolves/checks the platform credential authority above, then locks the platform report-state row. Cleanup locks report state without requiring a current provider credential, binding or permission. No credential or parent lock is acquired after a job lock. No collection transaction writes a Facebook User-credential row.
4. Lock job rows in ascending ID, then operation/checkpoint/capture rows and measurement rows in stable key order.

No database transaction spans provider HTTP. The protected service credential read checks the claim and its captured authority before spending a call; the result RPC repeats the complete fence atomically with persistence. It checks owner/platform/active/reauth state, collection switch and target eligibility, job generation, claim token, current credential authority and `lease_until > clock_timestamp()`. Check the wall clock again after any blocking lock and immediately before writes. A stale refusal changes no measurement, checkpoint, receipt, retry/success timestamp or report revision. Record sanitized refusal events through the operational logger outside the refused transaction. Do not use serialization SQLSTATE `40001` as an application refusal that PostgREST might retry; use explicit nonretryable domain codes and test them through HTTP.

## 3. Concrete tables and business keys

Create the following explicit families. `fb_` tables check `platform='facebook'`; `threads_` tables check `platform='threads'`. No dynamic-SQL table-name selection is required in runtime RPCs.

| Purpose | Facebook | Threads | Business identity |
|---|---|---|---|
| Queue | `fb_analytics_collection_jobs` | `threads_analytics_collection_jobs` | owner/account/provider-calendar due date |
| Operation receipts | `fb_analytics_collection_operations` | `threads_analytics_collection_operations` | job/generation/operation key |
| Inventory continuation | `fb_analytics_collection_checkpoints` | `threads_analytics_collection_checkpoints` | job/generation |
| Response capture authority | `fb_analytics_captures` | `threads_analytics_captures` | owner/account/capture ID; unique account capture sequence |
| Report consistency | `fb_analytics_report_state` | `threads_analytics_report_state` | owner/account |
| Daily measurements | `fb_page_insight_daily` | `threads_account_insight_daily` | owner/account/`metric_date` |
| Post snapshots | `fb_post_insight_snapshots` | `threads_post_insight_snapshots` | owner/account/provider post ID/UTC `captured_on` |
| Profile observations | `fb_page_profile_observations` | `threads_account_profile_observations` | owner/account/capture ID |
| Individual metric values | `fb_analytics_metric_values` | `threads_analytics_metric_values` | one metric per typed daily/post/profile parent |
| Exact totals | `fb_analytics_period_totals` | `threads_analytics_period_totals` | identity described below |

Queue rows store `due_at`, `next_due_at`, due date/timezone, generation, lease/claim, attempts, retry deadline and captured credential authority. Due date is the pinned provider-calendar date, **not** Instagram's Kuwait day or the UTC response-capture day. The calendar determines the next deadline across DST. Only a receipt strictly before `next_due_at` can satisfy its due date. A late repair retains its original missed deadline.

Report state stores the positive `report_revision`, `retention_floor`, provider calendar/timezone and next capture sequence. Calendar changes require explicit version/migration review; they cannot silently repurpose a daily key. All range indexes start with owner/account, then measurement date or capture day. Post ordering additionally indexes `(published_at DESC,platform_post_id DESC)` with capture-day lookup. Profile selection indexes `(observed_at DESC,id DESC)` after owner/account. Queue scans index eligibility/state/next-attempt time; all composite foreign keys have supporting indexes.

Exact-total uniqueness includes owner/account, level (`account` or `post`), subject ID, canonical metric key, provider API version, provider timezone, normalized exact `since`, `until` and UTC capture date. Account subjects must equal the fenced platform account identity; post subjects must belong to that target's inventory. Require `since < until`, validated zone/bounds and an exact-period-verified registry cell. A 7-day and a 30-day total ending together cannot collide. An undated lifetime response cannot populate this table. Report selection requires matching definitions and exact normalized bounds; otherwise the metric remains unavailable.

## 4. Capture identity and per-metric persistence

Allocate a capture UUID and an increasing per-account sequence in SQL **before each provider request**. Bind it to the current job/generation/operation, credential authority and request window. That reservation is committed before HTTP. A new provider read always reserves a new capture; a persistence retry of the same response uses its original capture. An uncertain/crashed read does not permit a different response to reuse that ID. Capture metadata stores requested/received times and nonsecret definition/window references; never raw provider URLs, bodies, messages or credentials.

Use **relational per-metric values**, avoiding unenforceable foreign keys inside JSON. The daily/post/profile tables are envelopes with a UUID primary key and a composite unique `(id,user_id,social_account_id,platform)`. Each platform's metric-value table has three nullable typed parent columns, `daily_id`, `post_snapshot_id`, `profile_observation_id`, a `num_nonnulls(...)=1` check and three explicit composite foreign keys to those envelopes. Partial unique indexes enforce one canonical metric key per nonnull parent. Each scalar metric row also has a composite foreign key to its owned capture. The exact-total table stores one scalar metric with the same provenance/capture foreign key directly, since metric key is already part of its business identity. JSON is only the RPC/report serialization; it is not a second stored metric authority. Each scalar metric has:

- canonical metric key and `{status:'available',value}` or `{status:'unavailable',reason}`; partial aggregates are derived by the report, not faked as complete stored daily cells;
- provider metric, API version, window kind, provider timezone and exact bounds where applicable;
- capture ID/sequence, actual observation time, collection time and an allow-listed source/evidence identifier.

SQL rejects unknown keys/fields, inconsistent status/reason/value combinations, negative/non-safe count values, malformed windows/zones, cross-capture ownership and arbitrary source strings. Capture sequence/time/window provenance is resolved from the referenced capture, not trusted as independent payload authority. SQL source/metric whitelists come from reviewed probe evidence; a caller-supplied `capability:'available'` is never proof. Application serialization uses the canonical contract and is checked again at the RPC boundary. Missing permission, `reauth_required`, provider failure, unsupported capability and omitted value retain their separate canonical reasons. Genuine zero is available.

Individual metric calls can update one daily/post envelope without erasing sibling metric rows. Compare capture sequence **per metric**, not only at envelope level. A lower sequence cannot replace a newer metric. Post metadata has its own owned capture foreign key and accepted sequence. Snapshot metadata and all accepted cells from one response commit together. Captures reference their owned job/generation/operation through composite foreign keys; metric/envelope references to captures use restrictive deletion. Duplicate capture ID plus identical normalized payload is a no-op with the original receipt **only after the complete current claim/credential/rollout fence passes**; expired, superseded or revoked claims cannot use replay as a bypass. The same ID with different content is refused. Store only a database-authored digest of the validated normalized measurement payload for replay comparison, never raw provider bodies or client timestamps as ordering authority. A new accepted measurement changes the report revision; replay does not.

Profile rows preserve separate responses and actual observation times. Follow design §8.1's deterministic, per-metric valid boundary selection and 24-hour limit; reconnect does not invalidate accepted historical samples. Instagram's additive extension uses an `ig_analytics_metric_values` sidecar with the same three typed parent references to its existing daily/post/profile rows and an `ig_analytics_captures` authority relation tied to its existing job/generation. Its compatibility writer updates scalar legacy columns and provenance together through the existing claim fence; the sidecar is the unified reader's source and never overwrites a newer legacy capture. Legacy DTOs retain their numeric values. Missing legacy provenance maps to `not_collected` with an internal `legacy_unknown` source marker; do not invent permission/provider failure or verified source evidence. Add explicit composite parent keys where absent. No applied migration is edited.

## 5. Durable work and truthful completion

Jobs, operation keys and bounded inventory checkpoints follow the existing durable pattern, with platform-specific receipt schemas. Force/reconnect invalidation advances the job generation and preserves older-generation receipts as history. Continuation never resets completed operations. Claims capture fresh authority; every result-bearing mutation repeats the fence. Provider throttles persist by platform/credential authority across midnight, independently of the due date; they are not cleared by normal enqueue or retention.

Reuse the shared transport's explicit deadlines, call/body limits and sanitized failures. Worker orchestration reserves time for persistence and stops when a dependency has an unknown commit outcome. A subsequent claim inspects durable receipts before retrying. Store failures do not become empty inventory, successful operations or fresh sync state. Inventory incompleteness, unavailable expected metrics and retry lineage remain visible. Job success and metric availability retain the distinct acceptance rules in design §10; a seven-day gate cannot pass from an all-unavailable job or repeated retries of one due date.

Each platform has its own server-owned collection switch and target allow-list, checked in enqueue, claim, credential read and persistence. Retention has its **own** switch and separately approved target/deletion scope; it does not depend on collection activation, collection eligibility or a currently valid provider credential. Disabled/disconnected historical targets remain eligible for an approved retention cleanup under structural ownership and live-lease exclusion. Missing, malformed or unreadable settings fail closed with sanitized logs. Initialize switches false and lists empty. Create only inactive enqueue/drain/retention cron entries; schedules/cadences require separate reviewed manifests and owner approval under design §12.

## 6. Consistent reports and cursor invalidation

Assemble each persisted report page in **one SQL statement snapshot** over its state and measurements, including account ownership. Do not stitch separate REST reads whose snapshots can differ. Return the revision, pinned as-of instant and retention floor internally with the page. The report assembler emits the canonical public contract and computes freshness from accepted persisted receipts, not a recent live request or attempt time.

Persisted cursors use a distinct format/namespace from live provider continuations. Sign platform, owner/account, exact period/calendar, ordering position, report revision, as-of instant and retention floor. A continuation RPC compares the signed revision/floor in the same statement snapshot as its page query. Any accepted write or cleanup that changes visible history advances the revision atomically. Return an explicit stale/expired-cursor refusal and require a restart when it differs; never silently mix captures across pages. The first page after restart reads the latest valid revision. This is deliberate invalidation, not a promise to retain overwritten row versions. The existing `metaAnalyticsCursor.ts` only owns live provider cursors and is not sufficient unchanged.

## 7. Bounded retention and deletion order

The design owns the 365-day eligibility formulas, including exact-total eligibility and the profile anchor. Pin its UTC cutoff once per cleanup invocation; record the same cutoff in all receipts. Exact-total cleanup uses the design's **both** conditions (expired provider window and old UTC capture day), preserving windows overlapping the floor. Use one shared budget across both platforms: at most **50 targets and 500 child-row deletions per invocation**, with a **40-second** overall deadline and **5-second** per-RPC timeout. Counts do not reset per table or platform. A dry run uses the same predicates/fence/order, reports counts without deleting or advancing revisions, and does not authorize later deletion.

For each target, acquire §2's parent-first locks, inspect **all** its collection jobs, and skip if any unexpired lease exists, even on another due date. With the target fence held, no claim can appear until cleanup commits. Select valid per-metric pre-floor profile anchors deterministically; a row-level success flag is insufficient. Retained observations and exact/daily/post windows must survive the deletion predicate.

Delete dependent scalar metric rows of eligible post/daily/non-anchor-profile envelopes first, then those envelopes, then eligible scalar exact totals. Within each class use stable primary-key ordering and the remaining shared limit; every deleted child, including a metric row, consumes it. Parent eligibility is derived from the design's bucket/capture/observation cutoffs, not the child's creation time. Preserve valid per-metric anchors and their envelopes/captures. Then delete unreferenced old capture receipts; then terminal operation/checkpoint rows; then terminal jobs with no retained receipt/capture references. Job due dates or `created_at` alone cannot prove child data is disposable. All affected foreign keys remain valid after a batch stops midway. Never delete account rows, credentials, report-state rows, active jobs, retained anchors or shared throttle buckets. Advance the target revision and monotonic retention watermark atomically with visible cleanup; do not declare physical cleanup complete while eligible rows remain. A no-op batch does not invalidate cursors unnecessarily. Lock/read failures perform no deletion and produce a sanitized failure receipt.

Retention switches and cron remain off after migration. A reviewed dry-run report and separate exact-scope activation approval are required. Instagram/competitor retention is unchanged.

## 8. Required proof and implementation order

| Invariant | Required test boundary |
|---|---|
| Structural owner/platform isolation; browser cannot read/write raw jobs or provenance | SQL/RLS/grants plus real report RPC |
| Claim expiry, force/reclaim, reconnect/unbind and permission generation changes fence every result mutation | SQL concurrency sessions plus HTTP regression; no automatic retry of domain refusal |
| A Page token is not a User token; absent Facebook authority is not synthesized; Threads direct/refresh writes advance its epoch | Credential RPC/trigger and adapter fixtures, including failed/rolled-back writes and ABA reconnect |
| Duplicate response is idempotent; conflicting same-ID payload and older same-day captures cannot overwrite; sibling metrics survive | Worker → RPC → stored row → report round trip |
| Every canonical failure cause survives independently; zero stays available; legacy unknown is not fabricated evidence | SQL validation and all three report assemblers |
| 7/30-day totals remain distinct; exact-boundary matching; provider-calendar days differ correctly from UTC captures across DST | SQL uniqueness/selection plus canonical calendar fixtures |
| Valid follower boundaries/zero growth, stale/missing samples, deterministic ties and retained anchors | SQL selection and report fixtures |
| Report/collection and report/retention races either return one revision or explicitly invalidate the cursor | Multi-session SQL plus endpoint continuation |
| Cleanup skips live leases on any due day; claim cannot race into deletion; reconnect/delete causes no lock inversion | Multi-session SQL with bounded timeouts |
| UTC/provider cutoff edges, aggregate caps, partial child cleanup and foreign-key-safe order | SQL dry-run/delete comparison with more than 500 eligible children |

Following the source review and corrections below, C2 adds schema/authority fences, SQL tests and database types without changing runtime dependencies or activation. Migration merge and production application each require the owner's separate approval. Only after schema verification do C3 workers, C4 persisted reports/Instagram version negotiation and C5 shared UI adopt it. Capability evidence still gates platform admission; this ADR does not mark incomplete Instagram probes, full G-X, pilots or scheduled stability accepted.

## 9. Source review and author adjudication

An independent read-only architecture review checked the draft against the parent design, the binding/refresh SQL and current callers. It found four actionable gaps; all were accepted and corrected:

1. Retention inherited collection eligibility and live-credential checks. It now has its own approved scope and requires ownership/parent fencing/live-lease exclusion, independent of collection or provider credentials.
2. JSON capture references could not supply the promised composite foreign keys. Relational scalar metric tables now have explicit typed envelope/capture foreign keys and child-first deletion. JSON is only the transport representation.
3. Existing Facebook connection counters do not cover every raw account update. The monotonic admission guard now refuses direct security-field writes, with admitted OAuth/refresh/health mutation paths required to use the existing fenced definer writers before admission.
4. Exact-total retention lacked a predicate. The owning design now specifies both expired provider bounds and old UTC capture-day conditions.

The corrections also name Threads trusted-permission storage and require current-fence validation before replay. These are author-adjudicated changes after independent review; no second independent approval or passed SQL implementation is claimed. `docs-guard` verifies the current-state references; all new names are explicitly proposed schema.
