# YouTube Stage 3 — edit published details and publish with verified settings

22 November 2026 · Design proposed for independent debate · Heavy · One delivery. [Unified implementation plan](../plans/2026-11-22-youtube-stage3-edit-and-publish.md)

## Outcome and evidence

A channel owner opens any owned video in the existing library, including a video uploaded outside Postora, edits its details, and sees the verified result at the original watch URL. A creator publishing a new video sees what each selected provider can apply, what visibility will be requested, and the separate outcomes of the upload, thumbnail and first comment. Editing video bytes, replacing a video, analytics, comment management and moderation are outside this delivery. A new upload is always an explicit Create Post action with a new ID.

## Published edit contract

Extend the authenticated `youtube-resources` endpoint with two discriminated operations, `edit_snapshot` and `update_video`. Retain existing read envelopes, empty states, paging and query keys. An additive optional `edit_metadata` capability allows an old server/new client or old client/new server to browse. Missing capability disables edit. Reuse existing token refresh lease and refusal logging. Keep the gateway in infrastructure, mutation and cache policy in application, field validation in domain, and presentation in ui. Do not import Create Post upload defaults into a published edit.

| Account evidence | Browse and publish | Edit decision |
|---|---|---|
| Active native account, owned channel and recorded `youtube.force-ssl` | Retain Stage 2 read and upload decisions | Allow an edit snapshot if the channel and owner projection can actually be read |
| Native readonly or upload-only | Preserve existing eligible actions | Missing write grant. Reconnect the selected native account |
| No recorded grants, revoked token, needs reauth or no usable credentials | Existing independent capabilities | Unknown or reconnect required. No write probe and no unrelated permission loss |
| Managed Composio account | Its managed upload tool can express the subset below. Stage 2 browse is unavailable | Provider unsupported. Show explanation at account summary even when no detail can open |
| Deleted, inactive, foreign account/video, or changed channel binding | Scope each operation again | Generic not found, no resource existence leak. Retire the editor |

Google accepts `youtube.force-ssl`, `youtube`, or `youtubepartner` for update. Postora should use the verified native force-ssl grant it already requests. Neither readonly nor upload alone authorizes update. Broad and CMS delegated grants are outside the existing Postora consent contract. For native insert/thumbnail, the existing upload or force-ssl grants suffice at method level. First comment requires force-ssl and an eligible video/channel. Google may still reject an individual operation. [Update](https://developers.google.com/youtube/v3/docs/videos/update) · [Insert](https://developers.google.com/youtube/v3/docs/videos/insert) · [Thumbnail](https://developers.google.com/youtube/v3/docs/thumbnails/set) · [First comment](https://developers.google.com/youtube/v3/docs/commentThreads/insert)

### Field policy

The native editor exposes five fields. A small edit surface still needs a complete writable projection for each submitted part. Use the resource in its original language, without an `hl` overlay. Read the complete relevant parts as owner. Track absent, explicit false, empty and failed/incomplete reads separately.

| Google part and field | Editor | Request and preservation rule |
|---|---|---|
| snippet.title | Required text | Nonblank, at most 100 characters, reject angle brackets. Every snippet write includes current or edited title |
| snippet.description | Multiline, explicit clear | At most 5,000 UTF-8 bytes, reject angle brackets. Preserve line breaks. Empty string deliberately clears |
| snippet.tags | Ordered chips, remove all allowed | Validate 500-character aggregate with commas and provider quotes around tags containing spaces. Preserve case and order. Explicit empty array maps to verified clear semantics |
| snippet.categoryId | Category selection | Required for every snippet write. Show current ID even if absent from choices. Validate changed ID against assignable YouTube categories for the applicable region. No default on edit |
| snippet.defaultLanguage | Preserve | Copy exact value if present. Keep absent when truly absent. Do not modify associated localizations |
| status.privacyStatus | Private, unlisted, public | Require known current value, explicit destination, and confirmed transition. Preserve on other changes. Use no upload default |
| status.embeddable, license, publicStatsViewable | Preserve | Copy current writable values for status requests, including false. Refuse a status write when the owner projection cannot establish these values |
| status.selfDeclaredMadeForKids, containsSyntheticMedia | Preserve by omission | Google documents these two as explicit-set-only. Never derive the declaration from effective madeForKids or an absent boolean |
| status.publishAt | Protected schedule | If scheduled, disable privacy changes and direct owner to Studio. Snippet edits exclude status. No rescheduling, immediate publication via past date, or cancellation as a side effect |
| recordingDetails.recordingDate, localizations.*.title/description | Writable by Google, outside editor | Exclude their entire parts. No timezone conversion or translation rewriting |
| paidProductPlacementDetails.hasPaidProductPlacement, brandPartner | Outside editor | Exclude these parts. Explicit false has declaration meaning. Partner linkage is separate consent |
| snippet.defaultAudioLanguage, channelId, thumbnails, localized projection, effective audience, statistics, contentDetails, processing/file details, bytes | Read/display only where relevant | No request fields for these. Check channelId server-side. Never echo provider JSON wholesale |

For newly encountered fields in a touched part, distinguish known read-only/exempt properties from unknown mutability. Disable writes to that part until preservation is established. In particular, validate a title-only edit on a video carrying audio language/localizations and status-only on an owner-limited resource. Omitted mutable siblings may be deleted or reset, even when a UI calls the action a patch. [Update field list and exceptions](https://developers.google.com/youtube/v3/docs/videos/update) · [Partial updates](https://developers.google.com/youtube/v3/guides/implementation/partial) · [Resource constraints](https://developers.google.com/youtube/v3/docs/videos) · [Provider changes including paid placement](https://developers.google.com/youtube/v3/revision_history)

### Read, save and recovery

1. Authenticate the session JWT. Load the active YouTube account by `id + user_id + platform + is_active` in the service-role query. Resolve stored channel and native credential server-side. Accept only account ID and validated video ID for snapshot. Never accept owner, channel, OAuth token, raw Google part or URL from the UI.
2. Fetch a fixed owner projection by video ID. Require exactly that ID and `snippet.channelId === account.platform_user_id`. Verify the credential's own channel identity on every Save, using a bounded authenticated channels.list mine lookup. Return editable values, field restrictions, fetched time and opaque revision bound to owner/account/channel/video and a server-computed digest of the writable fields of the selected parts; exclude counters and read-only fields. Scope the session/cache to the active user. Failed read is a typed failure with no editable defaults.
3. Save input carries account ID, video ID, base revision, a strict changed-fields object and privacy confirmation bound to the base and destination if needed. Reject unknown keys, nulls, empty changes, over-limit input and ambiguous clear requests. Repeat ownership, capability and channel checks. Read the same provider representation, compare the revision, validate availability, project all writable siblings of touched parts and merge only deliberate changes. Submit one bounded `PUT videos?part=...` with original ID and the freshly read provider item ETag in `If-Match` only when the private-fixture rehearsal proves enforcement. A title-only request never includes status. A combined edit uses one PUT. Recheck account binding after refresh and immediately before dispatch.
4. A changed base or provider 412 means conflict. Never retry by substituting the latest revision. Test the provider actually honors the observed item ETag between pre-read and PUT. An in-process mutex, timestamp, hash or SQL lease alone cannot fence a simultaneous change in Studio. If support cannot be proven, keep editing disabled pending owner decision. If Google conclusively ignores the header, the owner may explicitly accept a residual race: reread and compare immediately before one PUT, verify after it, and disclose that concurrent Studio edits can still be overwritten. Never promote this fallback by default. [ETags](https://developers.google.com/youtube/data/getting-started) · [Precondition errors](https://developers.google.com/youtube/data/reference/rest/v3/core_errors)
5. Validate provider response ID. Re-read same owned video and verify intended fields and preserved siblings before reporting saved. Read-after-write mismatch, malformed success, timeout, worker termination, ambiguous 5xx or lost response enter reconciliation. Display current values on a fresh owner-bound read. Matching intent shows “Current details match your changes” without claiming which actor made the write. Different values require explicit review against a fresh baseline. An unavailable read leaves outcome unknown. No automatic mutation retry on reconnect, remount, token refresh or backoff. Authentication refresh before transmission may be retried once under the existing lease.
6. Distinguish invalid field (inline), forbidden setting (field unavailable), missing grant/revoke (reconnect), missing resource (close edit), quota/rate limit (show retry time if known), definitive upstream rejection and uncertain delivery. Fail-closed per-owner and project-wide mutation limits sized against the verified shared Google quota, bounded body and fetch deadline before dispatch. Fail closed if mutation limiter or account lookup fails. Carry sanitized request ID. Log authenticated refusals and uncertain writes with operation, reason and scoped identifiers, never drafts, URLs with credentials, provider bodies or tokens. Preserve existing anonymous abuse protection. Audit write readiness before provider dispatch. No browser service-role or raw upstream errors.

For example, a title-only save submits the following application payload. The gateway supplies authentication and the server derives the account owner, Google parts and unchanged fields.

```json
{
  "operation": "update_video",
  "account_id": "13a7bda5-e24f-4caa-8917-aa17f57e1671",
  "video_id": "AbcD1234eFg",
  "base_revision": "<opaque revision from edit_snapshot>",
  "changes": { "title": "Workshop recording, November" }
}
```

Use a separately budgeted mutation bucket (proposed 5 save attempts per 10 minutes and 30 per day per user, subject to review against actual project quota). Keep browse quotas independent. A refresh button performs a read. Retry-After permits another read or a newly reviewed save and never schedules a PUT. Translate a stale base or Google precondition failure to application `edit_conflict` (409). A possibly delivered write returns an explicit `outcome_unknown` result and request ID, including when the frontend lost the entire HTTP response. Client-side retries must be disabled for the mutation. The verification read can be retried with bounded backoff.

## Create Post evidence and target contract

`src/pages/CreatePost.tsx` assembles `YouTubeSettingsState`, invokes the managed-provider guard, validates uploaded media IDs, then inserts/updates `posts` with `usePlatformSettings.buildPostMetadata()`. `src/components/post/settings/YouTubeSettings.tsx` renders the controls. `useYouTubeThumbnails.tsx` produces browser frames and generated candidates. Processing reads stored metadata, resolves target account and dispatches native `youtubePublisher.ts` / resumable logic or `youtubeComposio.ts` with pinned tool `YOUTUBE_MULTIPART_UPLOAD_VIDEO`. The public REST/n8n and MCP inputs have their own adapters. Test their generated metadata as well as delayed jobs and legacy rows. The following keys omit the common internal prefix `youtube_`.

Preserve draft intent after target switches. Never silently discard requested settings or transfer native tokens to Composio.

### Ownership, durability and outcomes

- Initial `process-post/index.ts` queries media by IDs, checks read error, orders results and fails on missing/unsendable items. Add a post-owner predicate to the initial query as defense in depth. Independently verify owned storage path and bucket identity before any provider receives the media. The managed adapter may reuse only the URL returned by the authorized resolver after this validation, including on a CDN hit, or use the owned-source path. It must never use the service role to sign a raw media-row path. Require complete requested set, original ordering, scan state, authorized bucket/path and owner/workspace binding. Native continuation already loads row identity/version, checks owner later and uses session fencing. Pass expected owner into that query too. Bind thumbnail media IDs independently. Apply equal controls before passing a URL to a managed tool, including redirect/host and bounded byte policy. A foreign or missing item yields the same safe unavailable result. A query error yields retryable preparation failure, never empty media or a fallback URL.
- Keep #441 admission, external URL policy, source/version pinning, range probes, byte offsets, account refresh, pending handoff, attempt/lease and durable receipt. Probe existing session on interruption and resume from provider-confirmed offset. Expired/unknown final response without a receipt goes to reconciliation. Never open another upload because polling timed out. Only definitely unsent work is safe for a fresh attempt. [Resumable protocol](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)
- Managed path has a 64 MiB local cap, 50-second budget, active workspace connection lookup, presigned transfer and tool ledger. These do not prove the outcome after execute loses its response. Before managed execute, persist an atomic target-specific result that the existing retry and sweep logic recognizes: a failed row with top-level `response_data.publish_outcome = "uncertain"`, and an additive attempt identifier in the YouTube receipt. Prove this row neither finalizes the parent early nor permits a stale writer to dispatch. After confirmation settle the same row by ID with the remote ID before thumbnail work, preserve unrelated evidence, and supersede the uncertainty marker only with durable confirmation. If the existing settlement contract cannot support this safely, use the migration gate in the plan. Scope by owner/post/account and fence current attempt. Recovery seeing possible send without ID must stop in needs-reconciliation. No native fallback or automatic resubmit. Only accept a recovered ID with authenticated provider evidence tying it to this operation. A similarly titled video is insufficient.
- Create Post's submitting ref prevents same-mount double-click only. Use a stable operation/post UUID per deliberate submission, retained across lost acknowledgements and reload for that draft/user. Prove through the authenticated browser role that the client can insert its generated posts.id and read back its own duplicate or ambiguous insert before relying on the existing PK. Resume target selection/enqueue idempotently only after confirming original immutable payload and targets. Conflicting payload requires explicit review. Two intentional new uploads must remain possible. Scheduler, retry and concurrent worker claims must converge per post/account.
- Store separate compact outcomes per requested follow-up in existing settlement evidence, with states not_requested, applied, skipped, failed or unknown and sanitized reason. Creator-only follow-ups may run once after receipt. Recovered receipt never replays a comment. Missing evidence after a crash means unknown, never failed/applied by inference. History/API return original video ID/link, requested privacy and verified effective privacy when available. Preserve upload success and existing response keys, including when follow-up settlement itself fails.

## Interaction design and acceptance journeys

1. **Find and edit.** From `/youtube`, the existing account picker, channel summary and video library select a video. In `YouTubeVideoDetail`, put “Edit video details” beside “Open on YouTube”. Keep current title, channel, visibility and fetched time visible. Open an inline card in place of the detail body with the same heading and watch link. A fresh snapshot loads before enabling inputs. Show “This changes the details of the same video.” Group Title, Description, Tags, Category under Details and Visibility separately. Edit is unavailable with an adjacent reason or a reconnect link to Profiles. Unknown capability or failed read never opens a blank editor.
2. **Review and save.** Show only changed values in a before/after review, with explicit “Remove all tags” or “Clear description”. Cancel returns focus to Edit. Save is disabled while pristine, invalid, fetching or sending. A dirty close/account switch asks Discard/Keep editing. Sign-out or forced identity switch immediately clears drafts and cancels stale completions. Keep failed drafts in memory within this selection. No local storage of video contents.
3. **Visibility.** Confirm every transition with channel, title, old and new visibility and named action (“Make unlisted”, “Make public”, “Make private”). Explain who gains or loses access: private restricts viewers, anyone with an unlisted link can share it, public is discoverable. Returning to private cannot recall copies or links already shared. Default focus on Keep editing. Scheduled video shows its protected schedule. Never widen visibility while clearing tags or refreshing.
4. **After save.** During PUT show “Saving…” then “Checking YouTube…”. Disable duplicate submits. On verified success restore detail, announce saved, refresh only selected detail and account list pages, preserve paging/selection. On conflict retain proposed values next to latest remote values, offer “Review latest details” and explicit reapplication to fresh base. On unknown show “YouTube may have saved this change” and “Check current details” (read only). On definitive rejection show actionable field error; on expired grant show reconnect; on quota show available retry time. A stale response from channel A cannot update channel B.
5. **Create and inspect.** On Create Post, select a native channel, add a video, choose Private and optional thumbnail. Show channel and requested privacy immediately above Publish/Schedule. Mixed/native-to-managed switch identifies incompatible non-default settings by localized names, with explicit change settings or remove channel. After enqueue show pending until receipt. In History show “Uploaded” with link and independent “Thumbnail failed” or “First comment unconfirmed” and reason. Uncertain upload shows “Check upload status”; no “Upload again” shortcut. Never label pending as published.
6. **Keyboard, small screen and Arabic.** Semantic form labels and descriptions, fieldsets for visibility, real buttons, logical tab order, visible focus, keyboard-operable tag removal and review. Focus first error with linked text. Announce saving/success via polite live region, blocking errors once via alert. Confirm dialog traps/restores focus, Escape returns to editing. At 320 CSS px stack controls and review values, wrap long titles and errors, keep actions reachable with keyboard displayed, avoid horizontal page scroll. Use logical spacing/alignment, Arabic and English strings, mixed-direction title/URL isolation and locale dates. Test zoom 200%, keyboard-only and screen reader announcements on real component composition.

One release is accepted only when the implementation plan's safety, provider and journey checks pass together. The manager's independent debate is the next decision point.
